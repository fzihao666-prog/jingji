# 周总结设计

## Context

本设计承接本轮已确认需求，权威行为见 `specs/weekly-training-reports/spec.md`。用户明确上一版没有达到期望，本次不能将“代码已有图表”视为布局被认可。

已观察的基础：

- `src/pages/ReportsPage.tsx` 有队伍/周次、基础下载、单独预览及AI编辑；目前不是专项/体能独立模板，也不是一次生成完整图文。
- `server/report/team-weekly-report.ts` 和 `shared/team-weekly-*` 已有训练、力量、测试、恢复及图表数据；当前仍是混合队伍报告。`strength_result_sets` 需通过父课次限制正式来源及权限。
- `team-weekly-ai.ts` 目前白名单发送训练/力量数值，不发送教练自由补充；需要显式修正此差距，不能只增加输入框。
- 现有队伍周报不保存历史，GET/POST PDF均按最新事实导出。个人报告已有独立 athlete_id 快照流程，本次不能改写其语义。
- `server/core/uploads.ts` 已使用multer/sharp，PDF已有本地中文字体和jsPDF；复用处理技术，不把训练照片挂到证件照入口或公开静态资源目录。

## Goals / Non-Goals

目标：教练少操作，领导易读；两类报告真实独立；首页有完整概括；自动选图、对比、收敛缺项；可编辑确认、同键替换、可追溯资料查询；附件可选且节省空间。

不包含：新建专项事实源、全项目统一科学评分、自动诊断或处方、修改训练计划、增加小程序入口、审核工作流、历史版本选择、照片识别或向AI上传参考PDF/训练照片。

## 布局方案

### 报告页

```text
报告
[专项训练周总结 | 体能训练周总结]
当前项目 · 当前队伍 · 周期（默认上一完整周，可修改）
▸ 补充信息（选填）
  训练阶段名称
  本周训练背景与教练观察（一个文本框，提示目标/反应/调整/下周重点）
  添加训练照片（自动压缩，可移除）
[一键生成周总结]
────────────────────────────────
生成后的图文预览（文字可直接编辑，内容按报告最终阅读顺序组织）
[保存并下载]
历史报告（项目/队伍/周次/类型）
```

AI配置可用且已有知情授权时随一键生成调用，不增加逐章节按钮。首次必要授权在生成入口清楚展示外发范围，不能把空着的补充变为阻断门槛。失败时保留已有成果；用户可补充文字、再次生成或保存基础稿。

### 最终报告

1. **首页**：队伍+专项/体能标题；日期与可选阶段；完整训练概括（目标与背景、实际情况、主要表现、问题、下周重点）；少量核心数据/关注事项。没有背景不虚构；现场意见与统计事实可辨识。口径说明不得抢占首页。
2. **训练全貌**：七天课表和必要训练结构/每日训练量图；数据量允许时同页，图旁有简短解释。
3. **本类型训练分析**：专项用当前项目有效指标，体能用主要动作、实际组次与外部负重容量；全员同指标合图，紧凑表补齐数据。两列或分页维持可读性，不产生每人一页。
4. **表现与恢复**：可比测试及必要恢复图，分别标单位；无对应数据只在数据情况处一句说明。仅报告有记录的事实，不用缺记录推断健康。
5. **结论与下周重点**：已有计划+教练意见，AI组织语言，不开新处方。
6. **附录**：完整队员明细、简要来源与规则、可选照片。无附件不产生空白页。

以上是主题顺序，不固定5/6页或要求每主题独占一页。正文优先图文而非长表；具体一页容纳人数、图高和照片列数用代表性合成样例验证后确定，不作为用户配置。

### 样例借鉴对应关系

| 样例 | 保留的组织优点 | 不照搬的部分 |
|---|---|---|
| 贵州皮艇队第43周 | 恢复目标、动作内容、队员反应、下周调整 | 真实身份、医疗建议和原始数值 |
| 贵州赛艇队第36周 | 赛前阶段统领总结，重点动作与队员图 | 自动判定减量科学性或比赛状态 |
| 贵州划艇队夏训第13周 | 专项表现与体能安排联系，详细动作处方作依据 | 将教练原因解释变成统计因果 |
| 四川激流队第1周 | 七天课表、类型时长、结构与负荷可视化 | 未核实占比、统一风险阈值或截图缩印 |

四份参考PDF本次已读取文字并查看图表页；仅作为版式与叙述参考，内容不得批量导入正式库或直接发给模型。

## Decisions

### 1. 独立模板、共用聚合基础

在既有周报契约引入显式 `reportType`（专项/体能，接口编码实施时统一定义）；以现有领域分类器筛选事实。恢复、伤病作为队伍背景独立处理，不计入所选类型训练总量；未分类事实不猜测归类，按需要简述数据情况。计划、测试和力量统计同步按类型与实际项目规则限定。`shared/`维护纯类型、图表数据和布局语义，避免网页/PDF两套计算。

### 2. 数据驱动选图与对比

报告聚合生成章节可用性、比较可用性及简短原因，渲染端不自行猜测。两周使用明示的一致人员范围及同口径事实；人数、记录覆盖或协议不可比时降为原始统计或略去。首屏不要求“是否对比”“选择图形”等设置。图表数据与解释引用同一统计，AI不承担计算。

### 3. 教练补充真正参与起草

教练补充保留原文为本地报告输入，将允许发送的训练观察标为非测量事实给模型，结合去身份化统计起草。字段及生成前提示明确发送用途，不静默丢弃补充。默认不外发身份、联系方式和健康细节；无法可靠分离的整段补充留在本地并进入教练观察，显示一句说明即可，不要求教练逐条确认。具体分离实现必须用代表性测试验证，不能声称简单姓名替换或正则能保证所有内容安全。

现有AI边界需要按本设计更新，同时保留原个人报告更严格的输入契约。模型输出仅为可编辑草稿；超时、数据变更、权限变化、格式错误均不得造成报告丢失或改写事实。总取消机制复用当前客户端。

### 4. 保存确认快照，同键原子替换

建议独立队伍确认报告表，唯一键 `(project, team_id, week_start, report_type)`。保存周期/范围说明、统计快照、最终文案、补充/阶段、规则与模板版本、照片清单、操作者、时间和并发修订。技术修订用于防丢，不产生用户多版本管理。

预览持有事实指纹；确认时复核。新生成不覆盖旧确认稿，保存/替换在事务中执行。历史按保存内容只读渲染及下载；旧模板版本可渲染或保持兼容，不因最新统计补录重算。列表分页，不预读完整JSON和照片。当前权限不足以查看某历史快照包含的对象时拒绝或按既有授权策略处理，不泄露旧全队数据、不静默改写快照。

### 5. 压缩附件与资源管理

独立私有附件入口，鉴权上传、解码验证、去元数据、方向修正、缩放及压缩。不保存不必要的原图，不自动发模型，照片保持比例；处理后清单用于预览与PDF。限制请求和解码资源是服务端技术保护，不向教练增加压缩质量/尺寸/存储设置。

数据库只存快照和处理后文件引用，PDF按需生成。文件处理先于确认事务准备；失败不得删除旧文件。确认成功后清理旧清单中无其他引用的文件。临时文件回收须检查引用和期限，不清理确认正文。备份同时考虑SQLite与照片清单，恢复不能只恢复数据库留下悬空引用。

## Migration / Compatibility

- 本次规划不执行迁移。实施时经既有幂等初始化机制新增队伍报告/附件结构，保留个人报告及训练事实；先备份，验证重复初始化和回退后数据保留。
- 明确旧混合周报入口与新增两类型契约的兼容策略；不能将旧请求无提示解释为某类型。
- 增量发布需同步网页和服务端；旧个人报告、小程序既有功能保持不变。
- 新功能失败时可回退代码并保留新增存储，禁止通过恢复旧整库覆盖新训练数据。

## Risks / 验证

重点检查类型隔离、教练补充外发、AI事实性与失败恢复、同键替换并发、历史快照权限变化、私有照片的格式/元数据/资源限制、附件替换回收、长名单不丢人、无数据不占页、中文及长文本分页。

使用内存数据库和合成材料进行定向测试及PDF逐页视觉检查；浏览器/真机实操依项目规则仅在用户明确要求时进行。当前环境没有OpenSpec CLI，本变更按仓库既有Markdown格式手工编写；未宣称通过CLI校验。

## 已知边界与实施裁量

无阻塞性产品问题。单页人数、图表大小、照片尺寸与压缩参数、列表页大小、临时文件期限及具体Schema/API命名由实现者按可读性与现有约定确定并验证；不得借此新增业务审核、必填项、自动删除确认历史或扩大AI外发范围。
