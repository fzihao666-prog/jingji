# 多项目适配技术设计

## Context

动机与范围见 [proposal.md](proposal.md)。本设计依据 2026-10-27 的源码与文档，不代表已经审计生产数据。

已观察到的边界：

- `shared/projects.ts` 已列出多个运动项目，但 `ProjectCapability` 仅覆盖三个水上项目，项目代码类型当前还被宽化为字符串。
- `shared/training-content-category.ts` 以内容文字推断类别，“专项训练”可落入水上；`src/pages/PersonalPage.tsx` 的分析器默认回退赛艇，部分页面仍比较旧中文项目名。
- `server/athlete/training-session-service.ts` 的强度输入固定为 U 系统；不能直接向其他项目推广。
- `training_sessions`、`test_sessions` 当前未直接保存发生时项目；主要通过运动员关联项目。已有课次包含平均功率和桨频字段，没有独立踏频字段。
- `metric_definitions` 已具备项目范围，`test_measurements` 已支持代码、单位和侧别；但 `test_sessions` 唯一键为运动员、日期、类型，同日不同协议会冲突。
- `server/analysis/physical-champion-service.ts` 已有项目、人群、协议和质量筛选；参考定义和雷达维度尚非完整多项目体系。已有估算参考不得被迁移自动标成已审核。
- `server/report/report-service.ts` 当前按指标、单位、侧别汇总不同协议，报告契约为版本 1。本次对新报告改变分组规则，旧快照不重算。
- 仓库是 React + Express + SQLite 模块化单体，网页和小程序共用服务端。现有导入、幂等、报告指纹和权限机制必须保留。

## Goals / Non-Goals

**Goals:**

- 项目身份、活动、采集、分析、评价相互分离，各层有明确的适用性和版本。
- 首批六项目具有最小但完整的可信闭环；未完成专业配置仍可使用已验证基础能力。
- 所有写入入口复用领域校验，所有分析读取同一正式事实；新增字段有明确旧客户端语义。
- 历史归属、同日多协议、幂等摘要版本及旧报告具有可实施的兼容策略。

**Non-Goals:**

- 不改变进程或数据库部署形态，不引入新运行时依赖，不开发通用规则脚本执行器。
- 不在本期实现转项、兼项、逐球比赛、设备时序采集或无来源的专业评分。
- 本次交付仅规划文件；不操作正式库、不修改运行代码、不将任务勾选为已完成。

## Decisions

### 1. 保留模块化单体，以项目注册表收拢差异

使用稳定项目代码，目录身份与业务能力分开。共享纯类型定义能力状态、活动代码、适用指标、强度体系与规则版本；复杂专项计算仍由显式代码实现。服务端提供当前授权项目的有效配置，客户端通过既有 API 封装获取，小程序需要的静态字典由现有同步脚本生成。

配置提供 `available`、`pending_configuration`、`unsupported`、原因和版本；参考能力状态还受当前有效已审核参考影响。配置不是权限，读写仍执行现有角色、区域、项目、队伍和运动员范围校验。

比较过逐页面增加 `if/else`、每项目复制一套应用和全面插件化。前两者继续制造差异和重复事实，后者超出当前规模；采用公共底座加有限配置和专项代码。项目精确字面量类型从只读目录推导，不用任意字符串代替校验。

### 2. 项目归属、活动和统计分类分别保存

建议增量增加以下结构，名称在实施中遵守现有命名约定，含义不变：

| 归属 | 增量信息 | 约束 |
| --- | --- | --- |
| 课次、测试 | `project_code`、归属确认状态、证据来源 | 新记录由服务端确定；历史允许空缺和待核实，不设置赛艇默认值 |
| 训练课次 | `activity_code`、领域类别、规则版本 | 活动可为骑行、水上、排球技术、力量、恢复或未知，类别不再仅由自由文本决定 |
| 强度记录 | 体系、分区、可选阈值版本 | 无强度填报时允许缺失；不同体系不自动换算 |
| 课次指标扩展 | 课次外键、指标代码、数值、单位、协议及质量来源 | 仅承载有类型的标量指标，不容纳任意业务对象 |
| 测试上下文 | 规范协议标识和版本、上下文签名、测试序号 | 协议文本原文保留，同日不同协议或重复试次可区分 |

时长、距离、RPE、平均功率等已有列仍为原事实来源，不再在指标扩展表重复写入。踏频首批作为课次扩展指标保存，不能重命名 `stroke_rate_spm`。测试仍写 `test_sessions` 与 `test_measurements`，力量仍写 `strength_result_sets`。每日恢复、身体测量和伤病保持运动员归属，不为了项目拆成重复副本；进入报告时按授权与明确时间范围关联。

项目决定可使用哪些活动，活动进一步决定哪些指标适用。通用身体测试与经配置的交叉训练指标可跨多个项目适用，不能直接拒绝全部非主项活动。空 `projects_json` 继续兼容现有“全项目适用”的含义，新指标必须明确声明通用或项目范围，并校验活动适用条件。

不采用公共表不断增加各项目专属列，也不采用全量 JSON 或所有事实 EAV 化。标量测量适合字典扩展，艇组成员、比赛回合等关系继续使用明确专项结构。

### 3. 同日多协议需要同步调整唯一键与业务去重

测试身份改为运动员、发生时项目、日期、类型、规范协议上下文及试次序号；测量仍从属于测试场次。未知历史协议不能擅自归一为某个正式协议，保留原测试 ID 与测量外键。

SQLite 不能直接删除旧表级唯一约束，因此此处允许一次受控重建测试表：事务内复制全部列与 ID，按依赖关系处理外键，保留索引及序列，提交前校验引用。不是删除并重建业务数据。同步修改创建、更新、导入去重和导出回导，否则只改 Schema 会导致调用层继续覆盖。

已知单位按指标定义规范化并保存源输入；不存在已确认转换的单位或协议只报错，不推算科学等价。协议或关键条件缺失的数据可作原始记录展示，不参与要求明确协议的趋势评价。

### 4. 统一后端处理路径并保留幂等入口

处理顺序：认证 → 范围校验 → 项目和活动解析 → 指标、单位、协议及质量校验 → 规范化 → 短事务内复核及去重 → 正式写入 → 统一查询与分析。

新增本人训练继续由账号确定运动员；教练与导入沿用既有运动员范围检查。AI 仍只生成草稿，确认前复核权限、项目和结构。沿用当前对外 AI 的去身份化、字段白名单和同意限制，不因项目适配扩大数据发送范围。

幂等记录增加摘要版本，新编号使用新版本规范化输入；已存在编号按保存的摘要版本解释原请求，权限和内容一致才返回原响应，不在升级后重新分配课次。若旧编号的请求内容变化仍返回冲突；不能先要求新字段齐全再识别已完成旧请求。

### 5. API 采用增量契约和显式不可用结果

保留现有端点和认证方式，补充活动、强度体系、协议上下文与配置版本。客户端经 `src/api.ts` 和小程序现有请求封装访问。项目配置读取归入现有项目/字典 API 域，禁止由页面自行复制规则。

| 情形 | 对外结果 |
| --- | --- |
| 已授权的可用能力、合法数据 | 沿用端点现有成功状态及新增字段 |
| 非法、歧义、错项目或不适用字段 | 400，结构化字段错误及原因，不静默删除字段 |
| 角色或项目权限不足 | 沿用现有 403/404 隐藏资源策略 |
| 已知但未配置的专项操作 | 409，`CAPABILITY_UNAVAILABLE` 及原因 |
| 规则变化后无法兼容的旧请求 | 409，`CLIENT_RULES_OUTDATED` 及更新提示 |
| 预览/事实/修订冲突 | 保留既有 409 与修订前置要求，缺少必要修订沿用 428 |

旧客户端的纯通用课次可以标记活动未知。语义明确的历史水上输入由已知映射兼容；未知项目不能落到赛艇。不支持的原字段不能静默丢弃后成功保存。具体请求例与错误字段跟随现有测试契约补充，不为本规格额外引入 Postman 平台绑定或发布。

### 6. 首批项目交付范围

| 项目 | 采集与分析的最低验收范围 | 关闭或延后 |
| --- | --- | --- |
| 赛艇 | 既有水上、测功仪、艇型与有效协议测试；修复代码/中文别名及默认回退 | 未审核标准不得继续冒充正式评分 |
| 皮划艇 | 既有艇种、距离、组合成员和专项测试；独立能力判定 | 未审核雷达维度 |
| 激流 | 保留已有项目指标、门区或罚时数据语义，不与静水竞速混排 | 新赛事事件采集系统 |
| 公路自行车、场地自行车 | 骑行时长、距离、SRPE、实测平均功率 W、踏频 rpm、同协议测试趋势 | 功率曲线、FTP 推导及需原始时序的专业负荷 |
| 排球 | 技术、体能、恢复分类；时长、SRPE；带协议纵跳 cm 等已确认通用测试；可选位置 | 逐球统计、自动跳跃计数、位置冠军评分 |

首批闭环包括训练计划创建和实施确认、两端填报、模板校对及正式写入、查询与新报告。其他自行车分项只能使用已验证公共能力，不继承公路/场地专项规则。平均功率展示单课值及同条件趋势，不把课次均值的算术平均冒充全时段真实平均功率。SRPE 汇总附有效时长/RPE覆盖率，不与专业功率负荷相加。

### 7. 参考与报告按版本演进

扩展现有参考源和参考值结构，增加审核、有效期、协议及维度版本，不另建第二套冠军标准库。现有全局参考维护权限不扩大；草稿改动产生新修订，激活时检查适用范围重叠。精确条件优先于明确的开放条件，同等优先级冲突不评分。既有估算值保留来源，默认不进入正式评分；经审核的队内参考也必须清楚命名。

新报告契约升级为版本 2，按项目、指标、单位、侧别、协议及必要上下文分组；需要对比或评价时检查条件，纯原始展示不生成跨协议趋势。报告指纹纳入相关规则与标准版本，等待 AI 或保存时复核。版本 1 继续只读按原快照渲染与导出，不对旧值重新计算。网页、小程序及 PDF 同时兼容两个版本。

### 8. 分阶段启用与变更协调

实施顺序为：公共适用性与默认回退修复 → 事实/协议兼容 → 首批项目全链路 → 审核参考 → 发布门禁。每阶段可独立提交，但新项目完整能力只能在对应端到端契约验证后打开。

与 `simplify-coach-data-import` 共享导入模块，实施前以当前源码和任务状态确认重叠项，复用其修订、事务和人员映射，不恢复旧用途模板或逐人教练关系。与小程序页面刷新及伤病待办变更共享页面时仅调整项目语义，不重做其流程或视觉。

## Risks / Trade-offs

- [历史项目证据不足] → 待核实且不评分，保留授权内的原始记录；另行确认才可清洗，不把全部旧记录批量标为当前项目。
- [测试唯一键及外键迁移] → 副本演练、一致性备份、保留 ID、逐项完整性检查；失败不继续启动写入。
- [改造后历史专项统计减少] → 展示被排除的数据及原因，明确规则修复导致差异，不能为数字一致放宽协议规则。
- [专业标准尚无来源] → 基础闭环独立验收，参考保持待配置；来源链接和专业阈值需审核后作为独立数据配置交付。
- [旧客户端及幂等重试] → 摘要版本化、兼容未知活动、专项歧义拒绝；网页和小程序配套发布并保留旧快照读取。
- [一份规格涉及面大] → 按任务阶段设门禁，不在第一阶段堆叠比赛系统或所有自行车分项。

## Migration Plan

1. 在隔离数据库副本中统计表结构、约束、来源证据和受影响数量；不将真实身份数据写进仓库或外部工具。
2. 使用现有 SQLite 一致性备份机制，验证备份可读及恢复路径，记录旧版本镜像和兼容基线。
3. 增量添加可空归属字段、来源/规则版本、课次指标扩展及参考状态；只对可靠证据回填，未知归属保留待核实。
4. 单独演练测试唯一键重建，验证原 ID、测量外键、索引、重复业务键和导出回导；涉及停写时使用明确维护窗口。
5. 发布能兼容旧/新事实与报告的服务端及客户端，尚未验证的能力保持关闭；旧导入草稿按版本提示重新解析，已入库回执和首次提交响应保留。
6. 六项目隔离样本通过后按能力启用，核对正式统计变化原因与质量覆盖率；不以浏览器实操替代服务端权限测试。
7. 新字段启用前可回滚兼容代码并保留新增结构。启用后仅回滚到验证过兼容的版本；不兼容时先停写、备份新增数据再恢复，必须逐笔对账后重放，不直接恢复旧备份丢弃上线后的写入。

## Verification Strategy

- 规则和计算：在 `shared/` 附近扩展项目、分类、专项与参考定向测试，使用六项目、缺失、真实 0、协议差异及未知项目样本。
- 数据与安全：隔离 SQLite 覆盖跨项目/越权、原子回滚、同日多协议、迁移重复运行、外键和历史归属；覆盖旧编号重试及草稿修订冲突。
- 跨端契约：沿用网页和小程序现有测试，覆盖计划、填报、导入、新旧报告与 PDF 的项目语义。按影响运行 `npm run check`、`npm run mini:typecheck`、`npm run mini:dictionary-check` 及对应定向检查。
- 专项链路：复用 `special-training-check`、`special-test-check`、`plan-check` 等真实脚本，并明确其测试环境前提；不对生产环境运行写入型脚本。
- 默认不运行浏览器或真机实操；仅用户明确要求时执行，未实操部分如实说明。本文档生成只运行规格校验与 Diff 检查。

## Open Questions

- 首批项目的实际测试协议名称、位置字典以及参考来源材料由教练或管理者在配置时补充；未配置项保持待配置，不改变上述闭环和验收范围。
- 历史归属证据的覆盖率只能在获准的脱敏副本审计后确定；证据不足的处理规则已确定，不以审计结果为由自动猜测。
