# 教练导入链路实施设计

## Context

动机见 proposal.md。2026-10-20 规划基于当前代码与前一轮隔离审查，未操作真实业务库。已确认：

- `data-import-routes.ts` 下载静态统一模板；当前文件含 13 张表，运动员资料表 31 列。`src/api.ts` 通过现有封装调用 analyze、batch、items、athletes、commit。
- `data-import.ts` 同时处理标准模板、历史表格、人员查找、暂存与写入；标准表按姓名匹配；别名查询未以传入候选集合裁剪；候选使用规范化姓名作跨表关联键，缺少同名不同人区分。
- `updateDataImportItems` 只更新通用数值等字段，身体测量等提交从 payload 取值；校验路径不同导致只填距离预览通过而提交失败。普通日期检查未验证日期往返；有内容缺姓名的行直接 continue。
- 档案写入没有 conflictPolicy 参数，身体测量和恢复整行更新可用空白覆盖原值。测试写入会更新全局指标定义，须限制导入对共享字典的副作用。
- 批次 UNIQUE(file_hash, project) 让同文件共享一条记录；当前解析可能复用旧预览。前端数据表仅取 500 条，修正能力不能覆盖完整业务字段。
- 正式来源仍为 training_sessions、daily_wellness、strength_result_sets 及既有测试、档案表；不使用 training_records，不恢复 coach_athletes 在线读写。现有文件名 UTF-8/Latin-1 纠正须保留。

现有主 specs 库为空，新增两项能力；既有 coach-team-responsibility 变更已完成的队伍派生逻辑作为约束。

## Goals / Non-Goals

**Goals**

- 正式写入可由用户确认的预览准确推导；默认路径不覆盖已有非空业务值。
- 常规已有队员文件上传后一次确认完成，异常才增加操作。
- 在既有 Express、SQLite、React 架构内完成增量改造，旧统一模板可继续使用。
- 新流程显式确认绑定批次修订和数据差异，防止并发与旧客户端绕过安全检查。

**Non-Goals**

- 不新增上级审批、账号自动开通、AI 推断、跨项目批量导入、清空已有字段、全局指标管理或导入即转队。
- 不新增“一键撤销已入库数据”；当前批次放弃/删除功能须保持既有授权与语义，不扩大为本次新能力。
- 不批量修正历史正式测量、重复人员或原身份证备份，不引入运行时依赖或第二套正式数据源。
- 不将队员资料模板变成完整人员档案编辑器；常规已有队员模板只含最小关联字段。

## Decisions

### 1. 规范化模型是唯一可提交数据

按 itemType 定义受限的领域联合类型：人员引用、规范化业务字段、字段是否实际提供、输入有效性、来源 sheet/row/cell、派生字段来源。`shared/` 只放两端必须共用的纯类型、字段字典和纯校验；数据库查询、权限和合并留在 server。

把解析、人员解析、字段校验、差异计算、正式写入逐步拆到 `server/data-import/` 的小模块，原入口继续编排，不一次性改写所有历史解析器。历史解析输出也转为同一领域模型。

字段输入至少区分 absent、valid(value)、invalid(raw)，不能仅靠 null。通用 valueNum 仅对单指标记录作为业务值；身体测量、恢复、训练等使用字段对象。兼容旧 valueNum 修正只在单指标类型有唯一映射时转换，否则返回 FIELD_PATCH_REQUIRED。请求按类型白名单校验，拒绝未知字段和超限条数，不继续 slice 静默截断。

校验统一返回 code、severity、field、sheet、row、cell 和用户消息。原业务事实/字典已有硬范围作为阻断，建议复核区间仅警告；不从模板说明独立复制另一套标准。普通日期用真实年月日往返校验；标准模板禁止隐式年份推断。数值字符串先判断 trim 后是否为空，再按允许单位解析。

不采用“只在页面修正显示值”：它不能保护 API、脚本和旧客户端写入。

### 2. 以人员引用隔离同名与跨表关联

新版模板包含只用于关联的 `系统运动员编号`（复用运动员内部 ID 的字符串表达，非登录账号编号）；它不是权限凭证。现有人员行按编号、当前可访问集合、项目、队伍及姓名一致性验证。模板元数据只帮助识别，不作为可信鉴权输入。

无编号时，解析当前项目/队伍内唯一规范化姓名；生日若提供用于冲突核对，不因缺生日拒绝既有唯一人员。多个候选进入 ambiguous 状态，无匹配进入 proposed-new。别名必须先按同一可访问集合裁剪。错误响应不返回范围外身份。

每个可识别人员使用独立 personRef。已有人员可基于 athleteId；新人员基于项目、有效队伍和规范化姓名生成批次引用；缺队伍且存在同名歧义时保留独立待决记录，不合并猜测。跨表只联动已明确的 personRef，禁止仅按 rawAthleteName 批量更新。

候选改名、映射或选队后重新计算引用、重复与差异。用户可明确映射已有人员或确认新建，创建前在事务内再次查重并检查 active、身份冲突和范围。没有编号仍无法区分的同队同名者须人工选择，不默认创建另一人。

队伍默认优先级：文件内有效权限队伍 → 下载/上传时显式选择的有效队伍 → 唯一可用队伍。明确的非法值不得回退。新建及档案变更复用已有权限与身份校验；原有转队流程单独处理，不在本次导入里修改已有 team_id。

### 3. 字段级合并与稳定差异确认

默认模式内部名保留 skip，用户文案改为“补全空缺，保留已有值”；update 表示“确认差异后更新”。统一合并矩阵：

| 正式值       | 本次字段   | skip       | update           |
| ------------ | ---------- | ---------- | ---------------- |
| 无正式记录   | 合法字段   | 新增       | 新增             |
| 正式字段缺失 | 合法字段   | 补全       | 补全             |
| 正式字段非空 | 同值       | 未变化     | 未变化           |
| 正式字段非空 | 不同合法值 | 保留并报告 | 仅确认的字段覆盖 |
| 任意         | 空白       | 不修改     | 不修改           |
| 任意         | 无效输入   | 阻断       | 阻断             |

0 是非空值。当前不暴露清空操作；未来需要时单独设计显式 clear 及权限。档案生日/性别等身份冲突单列，不因批量选择更新全部普通测量而自动批准。已有人员队伍不一致要求使用转队流程。

服务端生成 changeId 和差异摘要，包含目标业务键、字段、原值/新值摘要、batch revision 与确认上下文。客户端提交 confirmedChangeIds；服务端不得信任客户端提供原值。确认后的映射、数值、策略或正式值变化会使相关确认失效。新建人员显式提交 confirmedNewPersonRefs。

`preflight` 生成最新摘要和无写入冲突令牌，commit 在事务内重新计算与比较；只确认无冲突的请求无需额外弹窗。档案使用已有权限范围，避免导入比正常编辑拥有更多修改能力。

不用“SQL 全行 upsert”作为通用更新策略；由领域合并器给出实际字段变更，写入服务只应用批准的差异。同一业务键合并前检测文件内部冲突，不依赖行顺序。测试指标不得 ON CONFLICT 修改全局字典，未知代码要求先在既有指标管理中维护。

### 4. 业务键、派生值与回执

沿用并明确当前正式唯一键：

- 档案：athleteId；恢复：athleteId + date；身体测量：athleteId + measurementDate。
- 训练课次：athleteId + sessionDate + sessionOrder；新版训练模板明确课次序号，单课可默认 1，多课歧义阻断。
- 力量组次：明确 trainingSession 引用 + exerciseName + setIndex；新版同时提供日期、课次序号/名称，禁止只靠首个同名课次猜测。
- 测试：athleteId + testDate + testType 下的 metricCode + side；旧类型兼容保留，不能把不同测试类型合并。
- 伤病、竞技状态等沿用当前正式服务键；无自然唯一键者需使用明确记录引用或现有业务去重口径，不凭文本近似判重。

训练负荷与组次汇总复用既有纯计算规则，修改输入后重算派生项。备注、协议、RPE 等模板支持字段逐项核对映射，不能展示可填却在写入时丢弃；未提供不填默认实测数据。

回执按唯一规范化业务记录给出互斥分类：新增、补全、覆盖、未变化、保留冲突、主动跳过。含覆盖且同时补全的记录归覆盖，只有补全归补全，无写入且有冲突归保留冲突，其余相同归未变化。另列人员计数、字段变更计数、原输入行、文件内重复行和未填报行；一行展开多个指标明确展示，保留旧 imported/skipped 并说明对应口径。

### 5. 接口增量契约

复用现有 `/api/data-import`，所有前端调用通过 `src/api.ts`，服务端每次验证角色、项目、队伍、批次所有者和人员权限。拟定增量契约：

| 接口                        | 增量行为                                                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| GET /template               | 可选 purpose=profiles/training/tests/unified、project、teamId、athleteIds、testType；不带参数保留旧统一模板下载；动态模板必须按权限过滤        |
| POST /analyze               | multipart 增加 purpose、teamId、reparse=true；新页面明确重新解析；缺参数的旧调用按同上传者、文件、解析版本及上下文恢复可继续草稿，不跨账号复用 |
| GET /batches/:id            | 保留旧概要和兼容 items 响应；新增 revision、解析上下文、人员及差异摘要；读取也复核当前权限                                                     |
| GET /batches/:id/items      | 新增受限 page/pageSize/filter/query，返回 items、total、page、pageSize，稳定按状态与来源排序                                                   |
| PUT /batches/:id/items      | 增加 revision、按类型 fields 和 personRef；保存后返回新 revision 和重新校验摘要                                                                |
| PUT /batches/:id/athletes   | 接入 revision、personRef、match-existing/create 决策；保留可安全转换的旧字段                                                                   |
| POST /batches/:id/preflight | 新增只读预检；返回 revision、差异、业务计数和 confirmationToken                                                                                |
| POST /batches/:id/commit    | 增加 revision、confirmationToken、confirmedChangeIds、confirmedNewPersonRefs；保留 conflictPolicy 与原基本回执，增加细分 counts                |
| GET /batches/:id/errors     | 新增授权纠错 XLSX 下载，安全文本及可重新导入的辅助列规则                                                                                       |

新请求使用明确 400 输入错误、403/404 不可访问、409 版本/确认冲突、422 业务校验错误；响应包含 code、message 和必要的字段错误。拒绝信息不暴露其他账号批次。保留原状态字符串 reviewing/committed/failed/rolled_back，仅调整展示文案。

旧客户端不提供 revision 时，仅允许安全的默认合并及无歧义修正；服务端在事务内按当前值计算并执行，不覆盖已有非空值。旧 update 无最新差异确认返回 CONFIRMATION_REQUIRED；旧新建请求无明确确认返回 NEW_ATHLETES_CONFIRMATION_REQUIRED。revision 过期返回 BATCH_REVISION_CONFLICT；正式值变化返回 IMPORT_DATA_CHANGED；旧载荷无法可靠转为领域数据返回 REANALYZE_REQUIRED。版本错误返回最新摘要的安全部分，客户端保留本地修改并提示重新预检，不能静默重试覆盖。

所有新客户端调用同批次时只以当前 revision 保存；多页编辑按 itemId 累积补丁。查询分页不丢弃未保存编辑。更新批次后服务端返回统计而非依赖页面自行猜测错误已消失。

### 6. 用途模板与页面

统一字段字典驱动模板表头、必填规则、下拉与编辑器，模板有版本/用途/项目元信息，新增字段不写入身份证。用途定义：

- profiles：队员资料一表，突出人员编号、姓名、队伍及可选性别、生日；展开可选档案字段，导入已有人员修改需差异确认。
- training：训练课次、力量组次、恢复三表可按需填写，明确课次序号；先选填报日期可作为空日期默认，导入仍校验。
- tests：按测试类型选择标准测试、FMS、冠军模型或身体测量等适用表，保留字典说明，不要求填写无关表。
- unified：旧统一多表入口，标注高级用途，继续支持既有 XLS/XLSX。

已有人员选择全部/子集的当前权限名册；仅预填编号、姓名、队伍，业务输入为空，不导出历史测量和额外私人资料。预填名册行无业务输入列为未填报，不报缺日期。资料用途既有人员无资料变化计为未变化；新建行有姓名与队伍则进入新建确认。缺姓名但有业务值始终报错。

模板说明独立于数据区，示例不放真实填报行。动态模板由现有 ExcelJS 生成/导出能力实现；保留静态统一文件兼容，模板版本与字段配置同源，不依赖当前含机器绝对路径的 filled 模式生成正式模板。

页面沿用现有设计变量和组件，流程为选范围/用途 → 下载填写 → 上传检查 → 异常处理（如有）→ 确认结果。不强制额外向导步骤；正常文件一个摘要确认即提交。校对按字段而不是通用数字框展示，错误可保存，多页可达；同名映射按 personRef 联动。未保存离开提示、错误焦点、分页可访问名称、状态文字/播报一起验证。

错误文件保留必要输入和来源，辅助列使用明确保留名，重传排除说明及辅助列。输出文本以字符串而非公式写入；输入公式不由服务端执行，缺缓存值或依赖不可复算的公式须要求填写确定值，不伪造计算结果。

### 7. 批次生命周期与最小迁移

保留状态值，reviewing 内用阻断项/确认项表达可提交性，不另造审核人。增加 revision、parser/template version、purpose、上传项目/队伍/defaultDate 等上下文、personRef/确认及提供字段信息所需最小持久化结构；使用 JSON 载荷存领域数据时明确 schemaVersion。详细 DDL 按当前真实 schema 落地，不能为适配旧文档重建业务库。

移除 UNIQUE(file_hash, project)，改为非唯一的查找索引（file_hash, project, created_by, parser_version，结合上下文查找）。默认恢复只发生在同账号、同解析版本和完全相同上下文的安全草稿；reparse 创建新批次，旧批次保留。业务写入幂等由正式唯一键及差异决定，不给文件哈希赋予全局数据所有权。

SQLite 如需重建批次表以移除唯一约束，只允许在受控事务和维护窗口重建该表，保留全部 ID、状态、时间、外键和关联；不得全库重建、删暂存或顺便清理业务数据。备份和完整性/外键检查必需，失败回滚；维护工具与应用初始化各自幂等。

旧 committed 只读，不重新写回。旧 reviewing 加载时使用原始载荷及来源重建规范化字段并重新校验；无法恢复提供字段语义、人员身份或原始错误的批次要求用户重新上传。不能把旧确认自动迁移成新版覆盖授权，也不能自动修正正式历史数据。

### 8. 提交并发与授权复核

preflight 只读；commit 以 BEGIN IMMEDIATE 开始后重新读取状态与 revision，重新查询权限、范围、正式值和新建人员重复。已 committed 先验证访问权再返回原回执。针对草稿 revision 做条件更新；差异与令牌不一致时返回 409。事务涵盖新建、正式字段更新、来源、批次状态、回执和审计。

审计写批次、实体 ID、变更字段名、数量和策略，不记录生日、联系方式、原始业务行等敏感值。暂存和差异响应仅当前有权人员可见；文件上传大小、表数量和单元格限制保留，分页与补丁数量严格受限。撤权后不允许通过旧批次、错误文件、模板或别名读取范围外数据。

## Risks / Trade-offs

- 默认 skip 从整条跳过变为字段补空 → 明确修改页面文案、兼容说明和回执，测试两种策略，不能静默改变导入结果口径。
- 历史草稿缺原始输入与提供字段标记 → 只转换可证明可靠部分，其他要求重传，不猜测或强行提交。
- 同名且缺队伍/编号无法自动识别 → 保留一次明确的人员消歧，以正确性优先，不自动发明身份。
- 批次表唯一约束迁移有外键风险 → 只对隔离快照先演练，检查行 ID、外键、关联和恢复，正式迁移需按现有运维授权执行。
- 旧客户端覆盖请求会收到明确错误 → Web 同版本上线；盘点实际小程序/脚本消费者，错误可理解且不自动重试。
- 分页只减少页面与网络单页体积，解析仍在既有进程内 → 保留文件/单元格限制，用 1200 条代表数据测分页和解析，不擅自引入队列服务或性能数字承诺。

## Migration Plan

1. 在隔离 SQLite 建立历史批次与代表性业务数据，补回归，按阶段实施先完整性后流程。
2. 对兼容旧模板的规范化、差异预检、确认和迁移逻辑完成测试，再连接新模板和页面。
3. 发布前对实际数据库做受控一致性备份并停写/维护；演练批次表迁移及恢复，校验 foreign_key_check、integrity_check、历史主键与关联。
4. 协同发布 API、Web 和模板；旧版 update 请求安全拒绝；不得为恢复旧写法关闭新校验。
5. 在隔离环境验证完整下载填写上传入库链路；正式环境仅经授权进行最小核验，不向真实库填入演示数据。
6. 失败先保持停写并诊断；未提交迁移回滚；已提交且未有新业务写入时可恢复一致性备份。已有新写入时不能直接用旧备份覆盖，需单独制定保全方案。旧应用依赖唯一约束/载荷，禁止盲目回滚旧二进制或删除新批次。

## 验证与完成边界

两份 spec 的每个 Scenario 均须在实施记录中映射到单元、SQLite 集成、API 或浏览器检查，不能仅以“全测通过”替代覆盖说明。测试使用虚构队员和独立临时数据库，不读取 .env、生产身份资料或正式主库。

当前已存在的 22 项导入定向测试只覆盖部分行为，不证明上述新能力已实现。实施必须新增针对性覆盖；迁移、共享契约和权限变化运行必要检查。此文档为待执行设计，不启动实施或部署。
