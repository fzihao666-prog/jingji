# 实施设计

## Context

已核查：`accessibleAthleteIds` 目前对 SCC 和管理角色统一调用区域、项目、队伍交集过滤；教练页通过 `coachIds` 计算负责人数。`RosterPage` 同时编辑逐人教练关系和行政归属，不能整页删除。运动员查询两次读取旧表分别生成 `coaches` 和 `coachUsers`。注册审核、账号管理、运动员创建/编辑、数据导入仍有旧表写入。`db-initialize.ts` 还用旧表补齐历史账号权限和账号上级。

## Goals / Non-Goals

- 目标：责任关系唯一、变更即时生效、访问与负责一致，兼容已有数据库和必要客户端。
- 非目标：小组分工、主教练指定、教练分类改造、训练事实迁移、删除旧表、整体权限重构。

## Decisions

### 1. 服务端集中派生，页面不自行推断

在 `server/core/` 新增独立责任关系查询模块（建议 `coach-team-responsibility.ts`），统一解析有效队伍、教练授权及成员，输出可复用的 ID 集合/映射。复用现有数据库访问方式，避免每名运动员单独查库。`shared/` 仅承载必要纯类型；数据库查询不得进入 shared。

沿用 `user_team_permissions(project, team)`，以项目和队名解析队伍 ID，最终用 `athletes.team_id` 关联。当前任务不引入队伍授权表结构迁移。存在失效名称或项目冲突时拒绝匹配，并形成不含个人信息的数量级诊断；不得回退到仅队名、旧 `athletes.team` 文本或旧个人关系。现有队伍名变更若可用，必须事务同步授权引用并回归验证。

### 2. SCC 全队访问，管理委派仍受原有约束

`accessibleAthleteIds` 为 SCC 使用派生队伍集合，为 ATL 保留本人分支，为其他角色保留原有范围过滤。`hasAthleteAccess` 及调用它的查询/写入自然采用新范围。逐项检查另行调用 `permissionsAllowAthlete` 的教练业务边界，避免残留区域过滤导致“能查看不能录入”。不得全局删除该函数中的区域判断，否则会扩大管理角色权限。

行政区域描述账户组织与上级管理边界，不裁剪已有效授权给 SCC 的整队成员。此为明确的产品权限调整，实施前需按项目敏感路径规范获得对认证/授权相关修改的明确签署；当前规格请求不视为代码修改签署。

### 3. 关系计算与响应裁剪分离

先统一计算队伍教练关系，再以当前请求用户可访问运动员集合裁剪响应。不要用 `canManageAccount` 的候选教练列表计算实际责任关系，否则会漏掉同队协作教练。对有权查看的运动员，只沿用当前响应已有的最小教练身份字段，不附带教练其他队伍、账号配置或不可见成员。管理者的教练负责统计明确标注当前权限口径。

### 4. 兼容层明确拒绝逐人变更

保留 assignments 读取路由及响应字段，统一接入派生模块。原 PUT 仅保存行政归属；对旧 `coachIds` 先验证、集合去重比较，不同返回稳定 409，避免静默忽略并向用户误报成功。鉴权和输入校验先于写入，失败无部分更新。运动员接口旧 `coachId` 按 spec 兼容，新客户端不再提交。客户端 API 在 `src/api.ts` 集中调整。

### 5. 旧表退出在线使用，历史权限初始化单独处理

不得删表或清空真实记录。已配置账号不再使用旧关系自动补齐权限或调整上级。对“完全无权限配置”的历史账号也不得通过旧个人关系推导整队授权，须由有权限管理员显式补齐。新增演示初始化改为直接生成项目、队伍授权；不改真实训练数据。代码完成后逐个解释所有 `coach_athletes` 引用：只允许表定义和历史兼容测试，不允许在线读写或新演示写入。

## Risks / Trade-offs

- SCC 同队跨行政生源访问是预期范围扩大，必须独立权限审查并覆盖所有运动员级读写入口。
- 队名型授权已有脆弱性，本次通过项目约束和队伍 ID 匹配控制，长期转为 team_id 授权另立变更。
- 仅有旧个人关系、无明确队伍授权的账号不能无审核扩为全队权限，需由有权限管理员通过现有授权流程补齐；上线前只输出缺失数量，不读取或输出真实身份与生产库内容。
- 新旧版本混用可能收到明确 409，发布需同步 Web、小程序及 API；保留错误提示，不自动重试冲突请求。
- 旧表保存不等于可直接回滚：重新启用旧实现会恢复过时名单。回滚前须明确权限口径并验证，不能通过重建逐人关系假装无损回退。

## Migration Plan

1. 使用隔离数据库覆盖现有和缺少权限配置的历史结构，不操作生产数据库。
2. 实现派生模块、权限分支、统一响应和兼容写入规则。
3. 清理各新增/审核/导入在线写入并调整前端入口及提示。
4. 执行回归与安全/a11y 独立审查，更新 README 与架构说明。
5. 同步发布客户端与服务端；仅通过管理员现有流程修复已确认的授权缺失。
