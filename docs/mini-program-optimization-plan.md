# 竞迹微信小程序：功能与结构优化规划

> 规划基准：2026-09-24。现状依据小程序、网页端与服务端源码；本文是待实施规划，不代表功能已上线。

## 一、定位与目标

小程序服务训练现场的高频动作：**运动员看今天、填今天；教练看异常、找人、跟进；管理者随时看授权范围内的关键变化**。网页端继续负责大屏分析、批量处理、训练计划编辑、AI 草案审核、权限配置及导入导出。两端共用 Express API、服务端权限和正式训练事实，不建立第二套数据库或统计口径。

实施后应能回答三件事：运动员打开首页就知道今天该填什么；教练能快速定位未填报、负荷和伤病关注对象并看到原因；小程序中的计划、测试、恢复和统计与网页端相同条件下的数据一致。

## 四、信息架构与页面顺序

暂保留当前“训练总览 / 专项训练 / 体能训练 / 档案 / 我的”五个底部入口，先优化首屏和页面关系，再根据使用数据决定是否改导航。

1. **训练总览 = 行动首页**：运动员依次看到“今日是否已填报 → 记录训练 → 今日/本周摘要 → 趋势”；教练和管理角色依次看到“每日待办 → 关注对象 → 团队摘要 → 趋势”。角色只决定展示顺序，权限仍由服务端判定。
2. **专项训练 = 团队到个人下钻**：项目、队伍、日期条件固定可见；先团队训练量与强度，再运动员列表和个人最近测试。冠军参考与个人实测明确分开。
3. **体能训练 = 计划到执行**：选人后按“本周计划 → 最近执行 → 最近测试与教练目标 → 趋势”展示。无计划时提示在网页端由教练配置。
4. **档案 = 个人事实汇总**：资料、训练、测试、恢复/伤病分区；本人编辑入口放在资料区，返回业务页保留合法筛选条件。
5. **我的 = 账户与说明**：改密、隐私、退出等低频动作，不放业务统计。

所有统计卡标出时间范围、单位及缺失原因；项目切换时清空不适用的运动员选择。深层编辑和批量操作引导至网页端。

### M2：把网页成果带到手机

| 工作项               | 前提与边界                                                                              | 实施后的效果与验收                                                         |
| -------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 本周体能计划详情     | 复用已授权的 `GET /api/training-plans`；按周/日展示既有计划与更新者，字段以实际响应为准 | 运动员可看本周安排；网页修改后刷新可见；小程序不创建第二份计划             |

### M3：协作能力，逐项评审后立项

1. **恢复日报填写**：先确认网页/服务端录入流程、字段归属、修改窗口与权限，再新增带校验的写接口。运动员按明确日期填写，网页端可见；接口未就绪则保持 M2 只读。
2. **教练跟进记录**：如确需“已联系/待复查”，设计服务端事件、操作者、时间与权限，与自动待办规则分开展示。本地 `storage` 不能冒充团队协作状态。
3. **订阅提醒**：完成订阅授权、服务端触发条件、频率控制和隐私评审后再引入；提醒直达当前待办或本人填报，以服务端状态为准。

微信登录、设备直连、批量导入导出、复杂计划编辑、AI 生成与审批、账号权限配置不纳入本轮；如有需求应单独提出价值、权限设计和测试计划。

## 六、代码结构优化

1. **沿用现有公共层**：继续通过 `services/api.js` 发请求、`page-scope.js` 管筛选、`request-guard.js` 丢弃过期响应。新增页面按此约定接入，不再造 `page-loader`。
2. **按业务抽视图转换**：逐步把首页待办、填报、体能计划和恢复趋势的显示映射抽成无微信环境依赖的纯函数；只处理本期触及的页。
3. **统一状态与标签**：复用日期/单位/缺失标签、加载与重试、可点击运动员卡；`scope-filter` 只负责筛选交互，业务规则留在页面和服务端。
4. **接口先定契约**：新增方法先进入小程序 API 门面；核对响应形状、角色、项目及运动员访问范围。跨端字典以对齐测试防漂移。
5. **性能先测量**：记录首屏请求数、资源体积和真机加载时间，再决定资源裁剪、按需加载或分包；暂不引入新图表框架。

M0/M1 优先于 M2；M3 只在现场使用证据支持时启动。每期记录“基线、目标、实际值”，不在没有数据前承诺百分比提升。

验证使用仓库已有的 `npm run check`、`npm run lint`、`npm run test`、`npm run api-check`；影响训练计划、专项测试或体能结果时补相应定向脚本。小程序还需微信开发者工具和真机检查 ATL、SCC、管理角色、无权限账号，以及断网、快速切项目、空数据和跨端一致性。本文只规划工作，不把这些命令记为已通过。

## 八、实施风险与决策点

- **“已填报”不等于“计划完成”**：当前待办按当天是否存在有效课次计算；计划完成率须等计划与结果有稳定关联。
- **权限与项目隔离**：新增运动员级接口须在服务端复用访问范围校验；页面候选列表不能充当授权。
- **恢复与伤病解释**：展示数据、时间及来源，不输出诊断；演示、估算及低质量记录不进入正式对照。
- **草稿与隐私**：本地草稿不保存证件号、手机号、伤病明细或密钥；退出登录及切换账号时清理。
- **范围调整**：若首批用户主要受阻于登录、弱网或数据缺失，先完成 M0/M1 修复，再决定 M2/M3 投入。
