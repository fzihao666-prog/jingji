# 竞迹微信小程序：功能与结构优化规划

> 规划基准：2026-09-27（合并 2026-09-24 初稿与本轮网页端/服务端/市面平台对标分析）。同日更新：**P0-1、P0-2、P1-3 已实施并通过验证，已从待办移出**（见第四节「已完成」与第六节「已完成阶段」）；本文其余内容仍是待实施规划，不代表功能已上线。

## 一、定位与目标

小程序服务训练现场的高频动作：**运动员看今天、填今天；教练看异常、找人、跟进；管理者随时看授权范围内的关键变化**。网页端继续负责大屏分析、批量处理、训练计划编辑、AI 草案审核、权限配置及导入导出。两端共用 Express API、服务端权限和正式训练事实，不建立第二套数据库或统计口径。

实施后应能回答三件事：运动员打开首页就知道今天该填什么（**已具备**：今日状态卡 + 记录训练 + 恢复日报）；教练能快速定位未填报、负荷和伤病关注对象，并**在小程序内就地处理**（**已具备**：待办分组筛选与搜索、点人下钻、伤病/疼痛上报）；小程序中的计划、测试、恢复和统计与网页端相同条件下的数据一致（恢复日报已打通；分析类只读能力仍待接入，见阶段 1）。

## 二、现状与能力差距

### 2.1 结构现状

- 小程序 12 页 / 业务页约 1814 行 JS，5 个 Tab；高频写入口 4 个：本人训练填报（`pages/training-entry`）、本人档案编辑（`pages/profile-edit`）、伤病与疼痛上报（`pages/injury-report`）、恢复日报填写（`pages/wellness-entry`）。
- `services/api.js` 封装 30 个方法；服务端实际约 93 个端点，小程序接入仍不足三分之一。
- 图表为 WXML 百分比柱条，零图表库、零小程序依赖；无订阅消息、无分享、无触底加载、无分包。
- 4 个 Tab 仍有样板重复：`profile`/`special`/`strength` 已改用 `isPageCacheFresh`/`markPageCacheLoaded`，`pages/index` 仍自建 30 秒缓存判据（漏 `dataVersion`）；`page-scope.js` 尚无 `loadPage` 组合函数，`showTrendDetail`/`goToAthlete` 仍各页复制 3 份——阶段 0 未做。

| 案例                                                                                                                    | 官方资料中的做法                                           | 竞迹借鉴点                                                     |

这些案例提供交互参考。TrainingPeaks 的 TSS、WHOOP 的恢复分数和 Garmin 的训练状态有各自的数据与算法前提，竞迹不能直接复制其阈值、评分或“已完成”含义；高负荷阈值继续使用服务端唯一口径（`server/core/coach-daily-todos.ts` 的 600AU）。

**提炼三条可执行模式**：① 每日检查表（check-in）作为运动员首页固定动作（**已落地**：今日状态卡）；② 告警 → 对象 → 动作（alert to action）作为教练首页主线（**部分落地**：筛选与下钻已完成，直达动作仍缺）；③ 只读趋势必须带时间范围与缺数据状态（**待阶段 1 落地**）。

## 五、信息架构与页面顺序

暂保留当前五个底部入口，先优化首屏和页面关系，再根据使用数据决定是否改导航。

1. **训练总览 = 行动首页**：运动员依次看到“今日是否已填报 → 记录训练 → 恢复日报 → 今日/本周摘要 → 趋势”（**已实现**）；管理角色依次看到“每日待办（可分组筛选）→ 关注对象 → 团队摘要 → 趋势”，其中关注对象的**直达动作**仍待 P2-6 补齐。角色只决定展示顺序，权限仍由服务端判定。
2. **专项训练 = 团队到个人下钻**：项目、队伍、日期条件固定可见；运动员列表触底分页，接入最近专项测试与历史最好成绩（**待办**，归 P1-4 / P2-6）。
3. **体能训练 = 计划到执行**：选人后按“本周计划 → 最近执行 → 最近测试与教练目标 → 趋势”展示。无计划时提示在网页端由教练配置（**待办**，归 P2-6）。
4. **档案 = 个人事实汇总**：资料、训练、测试、恢复/伤病分区；本人编辑入口放在资料区，伤病与疼痛上报入口已放在此页（**已实现**），返回业务页保留合法筛选条件；恢复趋势与身体成分历史分区待阶段 1 接入。
5. **我的 = 账户与说明**：改密、隐私、退出等低频动作，不放业务统计。

所有统计卡标出时间范围、单位及缺失原因；项目切换时清空不适用的运动员选择。深层编辑和批量操作引导至网页端。

## 七、代码结构优化

1. **沿用现有公共层**：继续通过 `services/api.js` 发请求、`page-scope.js` 管筛选、`request-guard.js` 丢弃过期响应；新增页面按阶段 0 的骨架接入，不再各自复制（`injury-report`、`wellness-entry` 是最后两个自建骨架的页）。
2. **按业务抽视图转换**：待办分组、今日状态、恢复日报的显示映射已抽成无微信环境依赖的纯函数（`utils/daily-todos.js`、`today-status.js`、`wellness-form.js`）；下一步恢复趋势、身体成分与专项测试的显示映射照此办理。
3. **统一状态与标签**：复用日期/单位/缺失标签、加载与重试、可点击运动员卡；`scope-filter` 只负责筛选交互，业务规则留在页面和服务端。
4. **接口先定契约**：新增方法先进入 API 门面；核对响应形状、角色、项目及运动员访问范围；跨端字典用 `npm run mini:dictionary-check` 防漂移。服务端新增纯逻辑放独立模块（如 `server/athlete/self-daily-service.ts`）以便脱离数据库单测。
5. **性能先测量**：记录首屏请求数、资源体积与真机加载时间，再决定裁剪或分包；暂不引入新图表框架。

## 九、实施风险与决策点

- **“已填报”不等于“计划完成”**：今日状态按当天是否存在有效正式课次计算；计划完成率须等计划与结果有稳定关联（已实现的口径须继续守住）。
- **权限与项目隔离**：新增运动员级接口必须在服务端复用访问范围校验；页面候选列表不能充当授权。
- **恢复与伤病解释**：展示数据、时间及来源，不输出诊断；演示、估算及低质量记录不进入正式对照。
- **草稿与隐私**：本地草稿不保存证件号、手机号、伤病明细或密钥；退出登录及切换账号时清理。
- **范围调整**：若首批用户主要受阻于登录、弱网或数据缺失，先做 M0 性质的发布检查（生产 HTTPS、合法域名三件套、`NETWORK_DEBUG=false`、AppID/备案、隐私文案），再推进新功能。
- **验证命令**：`npm run check`、`npm run lint`、`npm run test`、`npm run api-check`、`npm run mini:typecheck`、`npm run mini:dictionary-check`；触及训练计划、专项测试或体能结果时补对应定向脚本。小程序还需微信开发者工具与真机回归 ATL、SCC、管理角色、无权限账号，以及断网、快速切项目、空数据和跨端一致性。未执行的阶段不提前记为已通过。
