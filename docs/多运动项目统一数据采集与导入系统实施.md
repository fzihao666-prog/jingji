# 竞迹｜多运动项目统一数据采集与导入系统实施 Spec V1.0

## 一、项目背景与目标

### 1.1 项目定位

竞迹是面向多个运动项目、多个队伍的综合训练管理与数据分析平台。

目前覆盖赛艇、皮划艇、激流回旋、举重、排球、足球、拳击、击剑、摔跤、田径、自行车、射箭、跳水、橄榄球等运动项目。

**禁止继续以赛艇、皮划艇等水上项目作为整个平台的默认业务模型。**

### 1.2 核心目标

建立一套可持续扩展的标准化数据采集体系：

**统一运动员基础档案 + 通用测试指标库 + 按运动项目和队伍配置的测试模板 + 统一导入流程。**

具体目标：

1. 所有运动项目使用统一的运动员基础档案模板。
2. 不同项目和队伍可以使用不同的测试指标组合。
3. 教练下载简单的 Excel 宽表，一名运动员对应一行。
4. 系统将测试宽表自动转换为标准化测试记录。
5. 自动预填已有运动员信息，减少重复填写。
6. 兼容现有教练 Excel、旧模板和设备数据导入。
7. 所有数据正确关联运动员、项目和队伍。
8. 尽量复用竞迹已有业务模型及导入能力，不建立第二套导入系统。

### 1.3 数据业务范围

竞迹运动员数据分为三个部分：

| 分类     | 业务内容                           | 本次范围                 |
| -------- | ---------------------------------- | ------------------------ |
| 基础档案 | 个人信息、身体信息、项目及组织归属 | 完整实施                 |
| 测试数据 | 通用体能、专项测试及历史成绩       | 完整实施核心流程         |
| 日常训练 | 训练课次、训练动作、组次及训练负荷 | 保持原有逻辑，仅保证兼容 |

本次不重构已有训练计划、训练课次、训练组次及训练统计系统。

## 二、统一运动员基础档案

### 2.1 模板结构

所有运动项目共用相同字段结构。

Excel 只有一张工作表，名称为：

**运动员基础档案**

### 2.2 字段定义

| 序号 | 字段名称     | 格式或单位     | 要求               |
| ---- | ------------ | -------------- | ------------------ |
| 1    | 运动员编号   | 文本           | 已有运动员自动预填 |
| 2    | 姓名         | 文本           | 必填               |
| 3    | 性别         | 现有枚举       | 建议填写           |
| 4    | 出生日期     | YYYY-MM-DD     | 建议填写           |
| 5    | 运动项目     | 系统项目名称   | 自动预填           |
| 6    | 所属队伍     | 系统队伍名称   | 自动预填           |
| 7    | 具体小项     | 文本或已有字典 | 可选               |
| 8    | 代表单位     | 文本           | 可选               |
| 9    | 输送单位     | 文本           | 可选               |
| 10   | 训练年限     | 年             | 建议填写           |
| 11   | 身高         | cm             | 建议填写           |
| 12   | 体重         | kg             | 建议填写           |
| 13   | 身体测量日期 | YYYY-MM-DD     | 记录身体测量时填写 |
| 14   | 籍贯         | 文本           | 可选               |
| 15   | 学历         | 文本           | 可选               |
| 16   | 最好竞技成绩 | 文本           | 可选               |
| 17   | 对应赛事     | 文本           | 可选               |
| 18   | 成绩日期     | YYYY-MM-DD     | 可选               |
| 19   | 备注         | 文本           | 可选               |

### 2.3 字段处理规则

- 每名运动员一行。
- 运动员编号采用现有系统稳定 ID，不因换队而改变。
- 姓名、项目、队伍是最小建档的必要信息。
- 性别、生日等其他字段允许后续补齐。
- 年龄由出生日期计算，不重复存储年龄。
- 训练年限优先复用现有字段，不因本次需求强制重构。
- 当前所属队伍、代表单位、输送单位必须区分。
- 最好竞技成绩作为竞技履历信息，不代替结构化测试记录。
- 身高、体重应保留对应测量日期和历史记录。
- 空白单元格默认表示未提供，不覆盖已有有效数据。
- 不把未知值自动填成0、无、当天日期或其他虚假默认值。
- 已有运动员仅预填身份与归属信息，不因下载和回传产生无意义更新。

### 2.4 健康数据

基础档案模板不包含详细伤病诊断、手术史等敏感字段。

伤病与康复资料继续通过现有受权限控制的业务模块管理。

不删除已有健康数据或康复功能。

## 三、运动员与组织关系

### 3.1 统一运动员身份

一名运动员在系统中保持一个稳定身份。

支持：

- 同一运动员关联多个队伍。
- 省队、国家队、集训队等不同组织归属。
- 运动员转队后的历史关系保留。
- 已有测试和训练数据不因转队而丢失。
- 根据实际业务关系查询当前所属队伍。

**不能仅凭姓名合并运动员。**

### 3.2 组织关联

优先检查并复用现有运动员、项目、队伍关联结构。

仅当已有结构无法支持实际多队关联及历史关系时，进行最小必要扩展。

历史归属至少需要能够表达：

- 运动员 ID
- 项目 ID
- 队伍 ID
- 关联状态
- 开始日期（存在真实依据时）
- 结束日期（存在真实依据时）

不得凭空为历史关联生成开始和结束日期。

### 3.3 四类教练角色

沿用竞迹统一的四类业务角色：

1. 主管教练
2. 专项教练
3. 体能教练
4. 康复治疗师

教练通过真实组织或个人关系关联运动员。

**运动员档案中的主管教练只展示实际关联的主管教练，未设置时为空，不得回退为其他角色。**

不要求教练在基础档案 Excel 中重复填写四类教练姓名。

## 四、统一测试指标字典

### 4.1 基本原则

测试指标统一定义，再由不同项目和队伍引用。

相同测试项目不因为所属运动项目不同而重复创建。

优先复用现有测试项目字典、编码及统计逻辑。

### 4.2 指标属性

每项测试指标至少应明确：

| 属性     | 作用                                       |
| -------- | ------------------------------------------ |
| 指标 ID  | 稳定唯一标识                               |
| 指标名称 | 中文显示名称                               |
| 指标分类 | 最大力量、爆发力、耐力、核心、功能、专项等 |
| 标准单位 | kg、cm、m、s、次、分等                     |
| 数据类型 | 数值、计时或现有支持的成绩类型             |
| 成绩方向 | 越大越好、越小越好、不评价                 |
| 测试协议 | 测试方法及必要条件                         |
| 适用范围 | 通用或指定运动项目                         |
| 启用状态 | 是否用于新模板                             |

同名但协议不同的测试不能无条件混合比较。

例如：

- 卧推实测1RM与估算1RM应区分。
- 测试重量与日常训练重量应区分。
- 手动计时与电子计时应明确协议差异。
- FMS 总分与单项评分不能混为一个指标。

### 4.3 通用体能指标库

初始候选指标如下：

| 类别         | 推荐指标                        |
| ------------ | ------------------------------- |
| 最大力量     | 卧推、卧拉、深蹲、硬拉、高翻    |
| 爆发力       | CMJ、SJ、立定跳远               |
| 核心能力     | 平板支撑、侧桥                  |
| 力量耐力     | 引体向上、俯卧撑                |
| 功能与灵活性 | FMS、YBT、坐位体前屈            |
| 速度与敏捷   | 10m、20m、30m冲刺及已有变向测试 |
| 耐力         | 已有标准化耐力测试项目          |

以上是可配置指标库，不代表所有运动项目必须测试全部项目。

### 4.4 项目专项指标

依据运动项目配置实际测试组合。

首批选择两个差异较大的项目验证：

**赛艇：**

- 卧推、卧拉、深蹲等通用体能测试。
- 测功仪2000m。
- 测功仪5000m。
- 30min@20spm。
- 其他已有且实际使用的赛艇测试指标。

**举重：**

- 深蹲等通用体能测试。
- 抓举。
- 挺举。
- 其他已有且实际使用的力量与专项指标。

具体测试协议、单位和指标组合以现有项目数据及教练确认结果为准。

不得擅自创建未经确认的标准或成绩参考值。

## 五、按项目和队伍配置测试模板

### 5.1 配置层级

采用三级配置：

**通用指标库 → 运动项目默认指标组合 → 队伍实际指标组合。**

配置规则：

1. 通用指标库管理标准测试定义。
2. 每个运动项目选择适用的默认测试组合。
3. 队伍可以调整自身实际使用的指标。
4. 新队伍默认继承所属项目的推荐指标。
5. 未配置队伍级组合时使用项目默认组合。
6. 不为每个队伍重复开发测试模板及导入程序。

### 5.2 配置管理权限

- 标准指标定义由系统管理员或授权数据管理员维护。
- 项目默认组合由授权项目管理人员维护。
- 队伍指标组合由授权队伍负责人管理。
- 普通教练只操作其有权限的项目和队伍。

第一阶段优先使用现有配置能力。

如尚无配置管理界面，允许先采用轻量服务端配置，不强制开发完整模板管理后台。

### 5.3 配置版本

测试模板应保存可追溯的版本或映射信息。

模板需要能够识别：

- 模板类型
- 模板版本
- 项目和队伍
- 测试指标 ID
- 指标单位
- 测试协议

导入时不依赖当前最新配置去错误解释旧版本模板。

已有合法模板和历史数据必须保持兼容。

## 六、动态 Excel 测试模板

### 6.1 模板结构

每次下载生成一张工作表：

**运动员测试成绩**

采用宽表结构：

**一名运动员一行，每个测试指标一列。**

前置固定列：

1. 运动员编号
2. 姓名
3. 所属队伍
4. 测试日期

后续列根据当前项目及队伍配置动态生成。

例如赛艇队：

运动员编号｜姓名｜队伍｜测试日期｜卧推1RM(kg)｜卧拉1RM(kg)｜深蹲1RM(kg)｜FMS(分)｜测功仪2000m(s)

举重队：

运动员编号｜姓名｜队伍｜测试日期｜深蹲1RM(kg)｜CMJ(cm)｜抓举(kg)｜挺举(kg)

以上仅为表头示例。

### 6.2 生成规则

- 根据当前授权项目与队伍生成。
- 自动预填已有运动员编号、姓名及队伍。
- 优先复用项目其他模板已实现的运动员预填逻辑。
- 动态列使用已有测试指标定义。
- 保持清晰中文表头与单位。
- 冻结表头、姓名列，合理设置列宽。
- 不使用影响解析的复杂合并单元格。
- 未测试项目保持空白。
- 不生成虚假的测试成绩。
- 模板中的映射信息需要服务器再次验证。

### 6.3 不同日期的测试

同一行默认对应同一测试日期。

不同日期的测试应分行记录。

不允许把多日测试成绩错误保存为同一天。

同一运动员可以出现多行，系统仍通过运动员 ID 正确关联。

### 6.4 控制模板宽度

默认只展示项目或队伍实际选择的常用指标。

指标过多时，允许按体能类别或专项类别选择导出内容。

不将所有运动项目的测试指标一次性放入同一份 Excel。

## 七、宽表转换为标准化测试记录

### 7.1 转换规则

教练上传宽表后，系统按指标列逐项解析。

每个有效测试值转换为一条标准化测试记录。

例如：

原始 Excel：

姓名｜日期｜卧推｜深蹲｜CMJ

张某｜2026-11-17｜95｜140｜42

转换后：

- 张某｜2026-11-17｜卧推1RM｜95kg
- 张某｜2026-11-17｜深蹲1RM｜140kg
- 张某｜2026-11-17｜CMJ｜42cm

此处数值为示例数据。

### 7.2 标准测试记录

复用现有 `test_measurement` 等业务模型。

每条记录应能够关联：

- 运动员 ID
- 测试日期
- 测试指标 ID
- 实际成绩
- 标准单位
- 测试协议（适用时）
- 来源及导入批次（已有能力支持时）
- 所属队伍或测试发生时的组织上下文

如果当前模型已有等价字段，不重复新增。

### 7.3 校验与转换

必须正确处理：

- 日期有效性。
- 单位及合法转换。
- 计时格式转换。
- 数值类型及合理范围。
- 真实零值与空值。
- 不同指标的成绩方向。
- 同名指标的不同测试协议。
- 同日多次测试的试次或批次区分。
- 重复导入与冲突确认。

所有单位和时间转换应采用明确规则，不猜测。

## 八、统一导入流程

### 8.1 标准流程

**选择项目和队伍 → 下载模板 → 填写 → 上传 → 校验预览 → 确认导入。**

上传后：

1. 识别模板类型、版本及字段映射。
2. 校验当前用户的项目与队伍权限。
3. 使用现有运动员匹配逻辑确认身份。
4. 解析基础信息或测试指标。
5. 将测试宽表拆分为标准化记录。
6. 检查重复、异常及缺失数据。
7. 仅对需要人工判断的问题进行确认。
8. 最终提交到现有业务存储结构。

### 8.2 运动员匹配

优先级：

1. 系统运动员 ID。
2. 已有明确的队伍及人员关联。
3. 姓名、出生日期等辅助信息。
4. 无法确定时由教练人工确认。

不能仅按姓名自动合并。

发现同名、跨队伍或多候选人员时，不直接猜测。

### 8.3 新运动员处理

允许编号为空的新运动员进入现有最小建档流程。

只要求创建最小必要的真实身份信息。

不强制提供身份证、完整学历、伤病资料。

新增运动员应与本次导入确认保持一致，避免预览阶段提前创建无效档案。

### 8.4 空值及更新

- 空白字段默认不覆盖已有数据。
- 真实0值必须保留。
- 只有预填身份、无实际填写内容的行不产生业务记录。
- 更新运动员档案采用必要字段合并。
- 更新身体测量数据保留历史。
- 预览中人工修正的最终值必须用于实际入库。
- 用户选择跳过的记录不得意外更新其他字段。
- 所有重复记录沿用现有确认规则。

### 8.5 提交安全

复用现有导入批次、权限校验及事务机制。

不允许部分失败造成不可解释的数据状态。

导入失败需要给出教练能够理解的行号、字段及原因。

## 九、运动员多队伍与历史关系

### 9.1 业务规则

支持一个运动员具有多个有效组织关系，例如省队、国家队或集训队。

运动员换队不重新生成身份。

历史训练和测试结果继续关联原运动员，并保留必要的发生时队伍上下文。

### 9.2 实施原则

先检查现有组织和运动员关联结构。

- 已支持则直接复用。
- 仅支持单队时，评估最小必要的关联扩展。
- 不为未来假设场景进行整体数据库重构。
- 不自动推断历史队伍关系。
- 不凭空生成历史日期。
- 不破坏现有项目与队伍权限隔离。

跨队伍关联不意味着所有相关教练可以查看该运动员在其他队伍中的全部数据。

权限仍应按照实际授权范围控制。

## 十、数据完整率与采集进度

### 10.1 目标

支持管理人员查看：

- 每名教练负责哪些队伍。
- 每个队伍有多少运动员。
- 哪些运动员缺少基础资料。
- 哪些运动员缺少指定周期内的测试。
- 各队伍的数据采集进度。

### 10.2 统计指标

建议区分：

**建档率：** 已建档人数 / 应建档人数。

**基础档案完整率：** 基础字段满足要求的人数 / 已建档人数。

**测试覆盖率：** 指定周期内完成应测项目的人数 / 应测人数。

具体规则：

- 应建档人数必须有可靠来源。
- 基础完整性规则可统一配置。
- 测试覆盖按项目、队伍及周期计算。
- 不同队伍的应测项目可以不同。
- 缺失数据不计为有效完成。
- 不为了显示100%而填充默认值。

### 10.3 开发范围

第一阶段可以先复用现有查询实现简单人数和缺失字段统计。

不强制建设复杂的数据采集管理平台。

---

## 十一、前后端实施与复用

### 11.1 前端

在现有数据管理模块中完成必要功能：

- 选择项目和队伍。
- 选择基础档案或测试成绩模板。
- 下载相应 Excel。
- 上传文件。
- 预览及处理异常。
- 确认导入。

优先复用现有全局项目、队伍筛选与上传组件。

不增加多余页面和重复筛选器。

### 11.2 后端

优先检查并复用：

- 运动员档案服务。
- 组织管理及权限服务。

### 第一阶段：统一基础档案

**优先级 P0**

完成：

### 第二阶段：动态测试模板

**优先级 P1**

完成：

1. 复用并补齐标准测试指标字典。

3. 支持必要的队伍指标组合。

### 第三阶段：队伍配置与数据管理

**优先级 P2**

5. 优化管理人员查看各队伍数据收集情况的能力。

验收目标：

新增队伍和运动项目时，主要通过指标配置及已有映射机制完成，不重复开发导入程序。

## 十四、AI Agent 执行要求

### 总原则

**最小必要修改、优先复用现有实现、保持前后端逻辑简洁、控制 Token 消耗。**

### 实施流程

**一次定位 → 确认现有能力 → 分阶段实现 → 必要验证 → 简要汇报。**

具体要求：

1. 从现有数据管理、模板生成、导入服务及测试项目字典入手，定向检查相关代码。
2. 已有功能能够满足需求时直接复用，不重复实现。
3. 优先沿用既有数据库结构及 API。
4. 仅在实际缺少能力时进行最小数据模型扩展。
5. 避免新增复杂配置后台、重复解析器及无关抽象。
6. 按 P0、P1、P2 顺序执行，不因后续功能阻塞基础档案落地。
7. 一次完成必要的代码审查和定向验证。
8. 不进行真机验证、不反复生成审查报告。
9. 不修改无关业务、不删除历史数据、不改变原有统计口径。
10. 如发现与现有项目结构不一致，以实际代码为准做最小兼容调整，并简要说明原因。

### 完成汇报

只需说明：

- 已完成的阶段与功能。
- 主要修改文件。
- 数据映射及兼容情况。
- 定向验证结果。
- 尚未完成或需要确认的事项。

不输出冗长的执行日志、重复分析和无关技术报告。

## 十五、最终交付目标

**面向教练：**

选择队伍 → 下载已预填运动员名单的 Excel → 填写基础信息或测试成绩 → 上传确认。

**面向系统：**

统一运动员身份 → 统一指标定义 → 按项目配置模板 → 标准化解析与存储 → 支持后续训练分析。

**面向管理人员：**

能够掌握每位教练负责的队伍、运动员规模、档案完成情况及测试数据覆盖情况。

最终形成适用于赛艇、皮划艇、举重、排球、足球、田径、击剑等多项目的统一数据采集体系。

**竞迹统一的是运动员身份、数据标准和导入流程；允许差异化的是各运动项目、队伍实际开展的测试内容。**
