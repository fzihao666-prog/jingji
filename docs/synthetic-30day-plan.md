## 数据模型与复用边界

训练事实使用 `training_sessions`、`daily_wellness`、`strength_result_sets`；测试使用 `test_sessions` 与 `test_measurements`；身体成分使用 `athlete_body_measurements`；专项成绩页面还依赖 `special_test_events`、`special_test_results`。

复用现有项目、动作、强度区间、训练分类及指标字典，复用写入字段规范和聚合函数；不写旧 `training_records`，不新增冠军标准。现有初始化逻辑可供结构与指标映射参考，不能直接作为本次运行入口：它包含历史种子删除和自动填充行为。现有 `daily-todos-example` 以固定少量运动员创建场景库，且标为参与正式统计，不符合本次可识别模拟数据的要求。

已有统计明确排除 `is_demo=1`、`demo/seed/estimated` 来源，并在聚合函数中二次排除演示数据。仅写演示标记不会满足图表展示要求；必须增加显式演示库模式。此模式需同时覆盖总览、专项、体能、档案及小程序使用的 API，而非只解除一处 SQL 条件。

团队时长、距离、负荷沿用同队、同日、同开训时段选代表课次的现有口径；个人统计保留本人课次。团队值不等同于个人值之和，验证时不能错误要求二者相等。团队 RPE 等指标按现有均值口径验证。

## 生成安排

- 固定种子 `jingji-demo-30d-v1-20261008`，按运动员 ID、队伍、日期、指标形成稳定随机子流；重复运行不依赖插入顺序。
- 同队共享周计划和开训时段，个人拥有稳定体重、能力与恢复参数，加上独立日波动。缺少年龄/等级时仅采用明确记录的模拟参数，不回填运动员真实档案。
- 每周安排 5 个主要训练日、1 个低强度恢复日、1 个休息日；队伍使用错开的减量阶段，个体可有小幅出勤与状态差异。休息日不强造课次，恢复日报仍可记录。
- 常规日以专项课为主，每周 2–3 次体能力量/耐力课，按项目选择训练内容；允许一日两课。具体数值范围在实现时依据项目既有校验边界与分布检查表固定，超出边界拒绝写入，不把演示参数作为训练建议。
- `sRPE = duration_min × RPE`，沿用项目舍入规则；距离与项目训练方式关联，陆上力量距离不伪造。平均功率、心率、桨频仅用于支持该字段的训练形式。力量逐组重量、次数与体能课关联，吨位由实际组结果计算。
- 睡眠、晨脉、疲劳和体重与前日负荷和个体基线相关联，但不机械同步变化；不生成伤病诊断。
- FMS、身体成分各安排 1 次/月；体能、专项测试各安排 1–2 次/月，并错开高负荷日。有真实既存同类记录时跳过冲突，不覆盖。
- CK、尿素氮、血红蛋白等实验室检测只安排 1–2 个采样日；乳酸仅放在合适测试/强度课采样日。字典中的 daily 表示可记录粒度，不作为每日强制采血频率。晨脉可每日，HRV 按演示采集安排记录。
- 仅生成当前项目可用的真实字典指标；缺乏小项映射时跳过专属指标并列入报告。无需为每个模块填充全部指标，也不伪造冠军对标。

## 写入、重跑与清理

- 先生成内存数据和统计预览，再通过现有数据库服务使用事务写入。
- 使用批次清单和稳定记录键实现幂等；检查同一运动员、日期、课次/测试类型等已有唯一约束。不使用覆盖真实记录的 upsert。
- 不复制默认库的业务事实，因此默认不会发生真实记录冲突；仍对目标演示库的非本批记录执行保护。
- 清理仅针对清单中的模拟记录及关联子记录；校验来源和演示库标识后按外键顺序事务删除，先提供清理预览，不清空整表。
- 生成工具属于项目受保护的脚本路径；用户确认本方案后才新增脚本及必要 package.json 命令，不修改现有构建/安装脚本或锁文件。
