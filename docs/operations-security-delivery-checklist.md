# 竞迹生产交付：安全与运维完善清单

> 目标：把当前可试用的训练数据系统，逐步完善为可承载真实运动员数据、可追责、可恢复、可持续维护的内部生产系统。
>
> 使用方式：每项由明确负责人完成后勾选；涉及真实数据、权限或上线的项，必须附上验收记录或截图链接。未完成“上线阻断项”不得对真实教练和运动员开放。

## 一、交付目标与边界

本清单适用于当前“React 单页应用 + Express API + SQLite + 本地上传文件”的单机部署架构。系统处理运动员身份、联系方式、紧急联系人、伤病、恢复、身体成分、训练和成绩等数据，应按照敏感个人信息的标准管理。

当前阶段的目标不是一次性建设大型运维平台，而是先形成四项最基本能力：

- 数据只能被有权限的人访问；
- 数据误删、机器故障或部署失误后能够恢复；
- 异常登录、批量导入、敏感导出和权限变更能够追溯；
- 服务故障、磁盘将满和备份失败能够被及时发现并处理。

## 二、角色分工

| 角色 | 主要责任 |
| --- | --- |
| 产品负责人 | 确认哪些字段必须采集、哪些角色可以查看、数据保留期限和交付范围。 |
| 技术负责人 | 审核代码安全、部署方案、备份恢复方案和上线门禁。 |
| 运维/部署负责人 | 管理服务器、HTTPS、环境变量、监控、备份、日志和故障响应。 |
| 数据监控总监 | 审核账号权限、导出记录、批量导入和异常操作日志。 |
| 教练代表 | 验证权限设置不妨碍日常训练录入、查看和导出。 |

## 三、分阶段路线图

| 阶段 | 目标 | 完成后可达到的状态 |
| --- | --- | --- |
| 阶段 0：上线基线 | 明确资产、数据、账号和部署责任 | 知道数据在哪、谁有权限、如何回滚。 |
| 阶段 1：上线阻断项 | 堵住公开访问、默认账号、密钥和备份风险 | 可在受控内部环境开放真实账号试用。 |
| 阶段 2：稳定运行 | 建立监控、审计、恢复演练和操作流程 | 可稳定运行并承担日常训练数据。 |
| 阶段 3：持续治理 | 最小权限、数据生命周期和定期审查 | 可长期交付，并能应对人员与规模变化。 |

## 四、阶段 0：上线基线（第 1 周）

### 4.1 建立资产与数据台账

- [ ] 列出生产服务器名称、IP/域名、操作系统、部署目录、Node.js 版本、启动方式和负责人。
- [ ] 确认数据库实际路径、上传照片目录、环境变量来源、备份目录和日志目录。
- [ ] 按“身份联系信息、健康与伤病、训练与成绩、账号与审计”分类所有数据字段。
- [ ] 明确生产、测试、演示环境；演示数据不得进入生产统计和导出。
- [ ] 建立《生产变更记录》，记录每次上线的时间、版本、操作人、回滚方式和结果。

验收：技术负责人能在 30 分钟内说明“真实数据在哪、由谁维护、如何备份、如何恢复”。

### 4.2 确认访问范围与最小权限

- [ ] 按角色列出可查看、编辑、导入、导出、删除、授权的数据范围。
- [ ] 对身份证号、住址、紧急联系人、伤病和身体成分单独确认查看权限；默认不向无关角色展示。
- [ ] 核验离队、转队、离职教练的账号停用流程和交接责任。
- [ ] 建立账号开通、权限变更、停用的审批记录。

验收：随机抽取 1 名运动员、1 名教练、1 名区域负责人，验证其数据范围符合授权且不能越权访问。

## 五、阶段 1：上线阻断项（第 1 至 2 周）

### 5.1 生产环境与密钥

- [ ] 生产环境使用独立的 `JWT_SECRET`，由受控环境变量或密钥管理工具提供，不依赖运行目录自动生成的密钥文件。
- [ ] `.env`、数据库、上传目录、备份目录均不进入 Git；部署账户只拥有必要的文件读写权限。
- [ ] 禁止生产环境生成或保留演示账号、演示训练数据和默认密码；上线前完成账号盘点并强制修改初始密码。
- [ ] API 服务不直接暴露到公网；仅由 HTTPS 反向代理转发，防火墙只开放必要端口。
- [ ] 配置证书自动续期，并验证 HTTP 会跳转到 HTTPS。

验收：在一台未授权电脑上无法直接访问 API 端口；仓库、日志和前端构建产物中搜索不到密钥、Token、真实身份证号或生产数据库。

### 5.2 登录、会话与敏感资源保护

- [ ] 将浏览器持久化 JWT 的方案改为安全 Cookie 会话：`HttpOnly`、`Secure`、`SameSite`，并为写操作增加 CSRF 防护。
- [ ] 会话设置合理有效期，并支持管理员停用账号后立即失效；必要时支持强制下线。
- [ ] 运动员照片不再由公开静态目录直接访问，改为经鉴权的文件接口或有效期很短的签名链接。
- [ ] 下载 PDF、Excel 和统一导出接口复核运动员范围权限，禁止仅凭前端筛选决定可导出范围。
- [ ] 为连续登录失败、密码修改、敏感导出和权限提升建立告警阈值。

验收：复制照片 URL 到未登录浏览器应无法访问；停用一个账号后，其已登录页面在下一次请求时返回未授权；不同角色导出的人员范围与授权范围一致。

### 5.3 上传与导入安全

- [ ] Excel、图片、PDF 等上传按真实文件内容校验，不只依赖文件扩展名或浏览器声明的 MIME 类型。
- [ ] 为上传大小、压缩包解压量、单次导入行数、并发导入数设置上限；将大文件导入移入后台任务或队列。
- [ ] 上传文件先进入临时隔离区，解析完成后删除临时文件；失败文件不得长期滞留。
- [ ] 导入批次记录上传人、源文件名、导入时间、影响记录数、错误数和回滚标识。
- [ ] 对批量更新、批量删除、覆盖导入增加二次确认和可恢复窗口。

验收：伪装为 Excel 的非表格文件被拒绝；超出上限的文件不会拖垮服务；一次错误导入可以定位批次并恢复受影响数据。

### 5.4 备份与恢复

- [ ] 每日自动备份 SQLite 数据库、上传照片和生产配置清单；备份文件加密后复制到与生产服务器隔离的位置。
- [ ] 设置保留策略：每日备份至少保留 30 天、每周至少 12 周、每月至少 12 个月；根据实际存储成本调整并记录。
- [ ] 数据库使用一致性备份方式，保证 WAL 文件、数据库文件与上传照片处于可恢复状态。
- [ ] 编写恢复步骤：新机器准备、恢复数据库、恢复上传文件、配置密钥、启动服务、核验数据。
- [ ] 每月至少一次在非生产环境完成恢复演练，记录恢复耗时、缺失项和改进结果。

验收：从任一最近备份恢复到测试环境后，能登录、查看运动员、打开照片、查询训练记录；恢复目标时间和可接受的数据丢失窗口已由负责人确认。

## 六、阶段 2：稳定运行（第 3 至 4 周）

### 6.1 监控、日志与告警

- [ ] 增加不暴露敏感信息的健康检查接口，覆盖服务进程、数据库连接和必要依赖。
- [ ] 配置进程守护、开机自启和异常重启；明确发布与回滚命令。
- [ ] 监控 CPU、内存、磁盘、数据库大小、接口错误率、响应时间、登录失败数、上传失败数和备份结果。
- [ ] 配置日志轮转与保留周期；日志不得记录密码、Token、完整身份证号、完整联系方式或完整导入文件内容。
- [ ] 为服务不可用、磁盘空间不足、备份失败、连续认证失败和导入失败发送给明确的负责人。

验收：人为停止服务、填满测试磁盘或模拟备份失败时，负责人能收到告警并按手册恢复。

### 6.2 审计与数据质量

- [ ] 扩展审计范围，至少覆盖登录失败、登录成功、查看敏感档案、导出、导入、批量修改、删除、权限变更、账号启停和密码修改。
- [ ] 审计记录包含操作者、时间、动作、对象、结果和必要的变更摘要；审计详情避免保存完整敏感字段。
- [ ] 审计日志禁止由普通角色修改或删除，并设置至少 180 天留存期。
- [ ] 为删除、覆盖导入和关键档案修改保留操作前后的摘要或版本记录。
- [ ] 每月由数据监控总监抽查导出、权限变更和失败登录记录。

验收：能够回答“某条训练记录由谁、何时、通过什么操作修改”，且不泄露无关敏感字段。

## 七、阶段 3：持续治理（持续执行）

- [ ] 每季度审查全部账号、角色、区域、项目和队伍授权，停用不再需要的账号。
- [ ] 每季度更新依赖并处理高危漏洞；更新前在测试环境执行类型检查、构建和核心流程回归。
- [ ] 每半年轮换生产密钥和服务器管理凭据，并记录轮换负责人及影响范围。
- [ ] 制定数据保留与删除规则：离队运动员、历史伤病、上传文件、导出文件和审计日志分别保留多久、由谁审批删除。
- [ ] 明确 AI 服务的数据边界：向外部模型发送的内容最小化、去标识化；AI 生成内容始终经过人工审核后写入正式训练数据。
- [ ] 发生数据泄露、误删、账号失控或服务器失陷时，按事件流程执行：隔离、止损、保全日志、恢复、通知负责人、复盘整改。

验收：每次季度审查都有记录；AI 调用、权限回收、依赖更新和故障复盘均可追溯。

## 八、正式上线门禁

以下任一项未完成，禁止接入真实运动员数据：

- [ ] HTTPS、反向代理、防火墙和生产环境变量配置完成。
- [ ] 演示账号、默认密码和演示初始化在生产环境关闭。
- [ ] 运动员照片、导出文件和敏感档案均经过服务端授权校验。
- [ ] 每日备份已连续成功运行 7 天，并完成至少 1 次恢复演练。
- [ ] 监控告警和故障联系人已配置，且测试过一次。
- [ ] 账号、角色和数据查看范围已由业务负责人签字确认。
- [ ] 上传与导入的大小限制、格式校验、失败处理和审计记录已验证。
- [ ] 安全审查、教练试用验收和上线回滚预案均已完成。

## 九、日常运行节奏

| 频率 | 必做事项 |
| --- | --- |
| 每日 | 检查备份结果、服务告警、磁盘余量和异常登录。 |
| 每周 | 检查导入失败、导出记录、权限变更和待处理异常。 |
| 每月 | 执行恢复演练，审查审计日志与账号清单。 |
| 每季度 | 权限复核、依赖漏洞处理、运维手册复盘。 |
| 每半年 | 密钥与管理凭据轮换，演练数据泄露和服务故障处置。 |

## 十、建议的执行顺序

1. 先完成阶段 0，明确真实部署与责任边界。
2. 再完成阶段 1 的密钥、照片鉴权、上传安全和备份恢复；这是接入真实数据的前提。
3. 随后完成阶段 2 的监控、日志和审计，把系统从“能运行”变成“出问题可发现、可追责、可恢复”。
4. 最后以阶段 3 的季度治理维持长期可用性，并根据教练的真实使用量评估是否将 SQLite 和单机文件存储演进为托管数据库与对象存储。

## 十一、当前代码库的已知起点

当前系统已具备密码哈希、登录限流、服务端角色与数据范围校验、部分操作审计、基础安全响应头、SQLite WAL 模式和上传大小限制。这些是良好起点，但不能替代上述上线门禁。

当前需要优先整改的具体点包括：浏览器使用 `localStorage` 保存 Bearer Token；运动员照片通过静态目录提供；生产密钥可退回到运行目录文件；数据导入主要按扩展名判断；审计尚未覆盖所有敏感读取与导出动作；仓库中仍存在演示账号初始化逻辑。实施时应以代码和实际部署环境复核为准。
