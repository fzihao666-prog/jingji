# 竞迹｜体育训练数据监控平台

竞迹是面向全国、省、市、区县各级体育管理部门与运动队伍的训练数据监控平台，覆盖训练数据采集与导入、训练负荷与恢复监控、体能与专项训练分析、运动员档案与冠军模型对标，帮助教练和管理者用统一口径评估训练效果、发现风险并制定训练计划。

平台由 Web 网页端、微信小程序和 Express 服务端组成，共用同一套账号权限与 SQLite 数据库。当前业务围绕赛艇、皮划艇（静水）与激流（回旋）开展，冠军模型与分析标准也按这三个项目配置；项目字典支持更多运动项目登记，各项目数据严格隔离。

## 1. 项目介绍

### 训练报告（周 / 月 / 阶段）

网页和微信小程序均从 **运动员档案 → 训练报告** 进入，选择自然周、自然月或自选日期（最多 90 天），点击“预览图表”。报告包含课次、时长、距离与 SRPE 指标卡，训练结构、每日负荷、测试首末数值变化及恢复趋势；缺失保留为“—”，不把覆盖率当作完成率，也不生成虚构风险阈值。

无需大模型即可预览、手写点评并确认保存。自愿勾选发送去身份化训练汇总后，可点击“生成 AI 点评”；使用服务端已有 AI 配置，姓名、联系方式、自由文本、伤病及恢复健康数据不发送。点评是待核对草稿，总计最多 250 字，人工确认后保存，不能据此自动修改训练计划。

“历史报告”两端共用，展示最近 50 份确认快照；原训练数据补录不改写旧报告，重新预览保存会生成新快照。网页可通过报告内“打印 / 保存为 PDF”使用浏览器打印功能，小程序查看同一份报告。当前测试变化基于统一 `test_sessions/test_measurements`，尚未归入统一测试表的数据不会自动出现在此报告；同指标、单位和侧别有两次记录即计算末次减首次，不要求协议一致或已填写，仅一次仍显示“—”。差值不代表进步或退步，也不保证测试方法可比；已有历史快照不重算。

小程序“历史报告”每条右侧提供“导出 PDF”：下载并打开该条已保存快照，包含指标、图表、测试变化、恢复趋势及点评，打开后可通过微信文件菜单保存或转发。导出不重新计算、不调用 AI、不公开文件链接。长周期图表每段最多 14 天。需在微信公众平台配置当前 API 域名为 downloadFile 合法域名；服务端部署需包含 `server/report/fonts/` 的开源中文字体及许可证。

发布时需同步网页、小程序和服务端代码；服务端在**既有数据库**幂等新增 `training_reports` 快照表，不创建第二套训练数据库，也不改写原训练事实。请先完成备份及旧版本兼容性检查，再部署；仅更新小程序而未更新后端会使报告接口返回 404。自动测试使用合成内存库，未调用真实模型或更改生产数据库。

### 1.1 定位与目标

- 为多层级训练管理体系提供单一事实源：训练课次、恢复日报、体能测试、专项测试、伤病与身体测量统一入库、统一口径统计。
- 让教练从“Excel 汇总”转向“在线监控”：团队与个人的训练量、强度、负荷、恢复和测试进步一目了然。
- 用可追溯的标准做对标：冠军模型参考值带来源、协议与单位，缺失数据不补零、不虚构评分。

### 1.2 核心使用场景

| 场景           | 说明                                                                                 |
| -------------- | ------------------------------------------------------------------------------------ |
| 日常训练监控   | 教练查看团队训练量、强度区间、SRPE 负荷、RPE 与恢复状态，识别高负荷与伤病风险运动员  |
| 训练数据采集   | 运动员在小程序填报训练与恢复日报，教练代填补录，测试现场录入，Excel 批量导入历史数据 |
| 体能与专项分析 | 力量处方维护与执行分析、体能测试趋势、专项测试成绩与专项训练结构分析                 |
| 运动员档案     | 个人成长档案、身体成分、恢复趋势、个人 vs 团队对比、PDF 总结与训练日志导出           |
| 标准对标       | 冠军模型参考值对标（体能八维参考、专项冠军模型与赛事参考成绩），输出达成度与差距     |
| 组织与权限管理 | 分级账号体系、注册审核、组织维护、操作日志审计                                       |

### 1.3 服务对象与角色

服务对象为各级体育管理部门、运动队的管理人员、教练员和运动员。系统内置五级五类角色：运动员仅访问本人；教练按授权项目与队伍覆盖全队；管理角色按行政区域、项目与队伍共同过滤数据。

| 角色         | 代码 | 数据范围                               |
| ------------ | ---- | -------------------------------------- |
| 运动员       | ATL  | 仅本人数据（可填报本人训练与恢复日报） |
| 队伍体能教练 | SCC  | 本人负责队伍的运动员                   |
| 业务负责人   | REG  | 授权区域、项目与队伍                   |
| 训练总监     | TD   | 管辖区域全部训练数据                   |
| 数据监控总监 | DMD  | 管辖区域全部数据、账号与操作日志       |

### 1.4 主要特点

- 权限在服务端强制执行：前端隐藏按钮不作为授权依据，越权请求返回 403；停用账号立即失效。
- 多渠道数据采集：微信小程序填报、教练代填、Excel 暂存导入、测试现场录入，全部落到同一套正式数据表。
- 导入先暂存后确认：Excel 解析进暂存区逐行校验，确认后事务提交，不覆盖既有真实数据。
- AI 输出始终是草案：AI 建议与结果识别需人工确认，服务端重新校验后才写入正式数据。
- 桌面端与移动端响应式界面；小程序复用同一 API、权限与数据库，不建第二套数据源。

系统采用模块化单体形态：前端、API、数据访问和分析模型位于同一仓库，生产环境由一个 Node.js 进程提供 API、上传文件与前端静态资源。

### 2.1 各模块职责

| 模块         | 位置                             | 职责                                                                                  |
| ------------ | -------------------------------- | ------------------------------------------------------------------------------------- |
| Web 前端     | `src/`                           | 登录、页面编排、图表可视化、PDF/Excel 导出；所有请求经 `src/api.ts` 发出              |
| 微信小程序   | `WeChat Mini Program/`           | 登录注册、训练总览、专项/体能页、档案、训练与日报填报、伤病上报、测试录入             |
| 后端 API     | `server/`                        | 认证（JWT）、权限裁剪、输入校验（zod）、业务事务、Excel 导入、AI 调用、文件上传与导出 |
| 数据库       | `data/training-monitor.db`       | SQLite（`node:sqlite` 内置模块，无 ORM），存全部业务数据                              |

### 2.2 运行拓扑

- **开发环境**：`npm run dev` 同时启动 Vite（`http://127.0.0.1:5173`）和 Express API（`http://127.0.0.1:8787`），Vite 将 `/api` 代理到 API；启动前预检 5173/8787 端口占用。
- **生产环境**：`npm run build` 产出 `dist/`，单个 Node 进程监听 `127.0.0.1:8787` 同时提供 `/api/*`、`/uploads/*` 与网页静态资源；由同机 Nginx 提供 HTTPS 接入，公网不得直接开放 8787 端口。

## 3. 核心业务流程

```text
注册申请 / 登录
       ↓
角色权限与组织绑定（角色 × 行政区域 × 项目 × 队伍）
       ↓
运动员 / 教练 / 队伍管理
       ↓
训练数据采集、录入与导入（小程序填报 / 教练代填 / Excel 导入 / 测试录入）
       ↓
数据校验、暂存确认与事务落库
       ↓
训练总览、专项训练、体能训练、生理生化
       ↓
运动员档案、测试分析与恢复趋势
       ↓
团队与个人对比、冠军模型对标
       ↓
辅助教练开展训练评估与计划制定
```

各环节的实际实现：

1. **注册与登录**：Web 与小程序普通注册均不收集身份证号；运动员和教练独立填写必填的出生日期、性别，生日使用日期选择器且不得晚于北京时间今天，性别沿用男/女选项。系统不收集或保存身份证号，运动员和账号通过内部 ID 关联。公开注册仅允许申请运动员或队伍体能教练，其余岗位由上级账号创建；“系统管理 → 账户审核”提供注册审核开关，开启时新注册需上级审核后方可登录；关闭时仅运动员可自动开通，教练仍需审核。自动开通的运动员可登录，但入队标记为“待核实”；在账户审核的“已开通”列表确认或拒绝入队，运动员名册可筛选待核实记录。拒绝入队会停用账号及档案、撤销会话，保留历史数据。待审核申请可先更正项目和队伍再开通。自动开通仅新建档案，同名同项目同队档案已存在时暂停开通并提示联系管理员，申请保留待审核。人工审核仅可关联同名同项目同队且性别、出生日期无冲突的无账号档案；档案空缺字段允许补齐，冲突需先由管理员核对更正。运动员开通及入队核实还须由行政范围覆盖其归属的审核人处理。籍贯只提供省市推测归属（estimated），不覆盖已确认的正式归属，缺少区县仍提示待完善。登录经限流与 bcrypt 校验后签发 JWT，每次请求重新确认账号状态。登录失败按稳定业务错误码返回（凭据错误、待审核、审核未通过、已停用、缺参、限流等，映射见 `shared/login-errors.ts`），Web 与小程序按同一映射展示提示；账号不存在与密码错误统一提示，停用状态仅在密码校验通过后返回，服务器内部错误一律不回传。
2. **权限与组织绑定**：账号绑定上级、行政区域（全国/省/市/区县）、项目与队伍。教练负责运动员由有效项目与队伍授权自动确定，同队跨省、市、区县生源及行政归属待完善的有效队员均纳入，不再逐人调配。同队多名教练各自覆盖全队，运动员入队、离队、转队或教练撤权后在下一次请求生效；负责队伍通过“账号权限”调整。管理角色仍按区域、项目、队伍交集裁剪，教练页的“当前权限内”人数只统计查看者可见运动员。行政归属可独立编辑，账号上下级不决定教练关系。转队时同步校验运动员上级，旧上级仍覆盖新范围则保留，否则改绑合法操作者；无法合法改绑则整次拒绝。
3. **数据采集**：见 3.1；所有来源最终写入同一组正式业务表，并以 `source` 字段保留来源。
4. **校验与存储**：Excel 导入先进暂存区（`data_import_batches` / `data_import_items`）逐行校验、人工校对与运动员匹配，确认后事务提交，失败不留半批。AI 生成或识别的结果永远是草案，需人工确认后写入。
5. **分析与对标**：统计接口按团队去重口径（同队同日同课次去重）聚合训练量、强度、负荷、RPE 与测试数据；缺失态统一使用“待采集/待参考/待核实/待配置”（依次表示缺测量、缺参考标准、标准未核验、模型未配置），不补零、不计算虚假达成度。
   - 小程序训练总览、专项训练、体能训练与运动员档案页在无运动员、无训练/测试或加载失败时保留现有模块；缺失指标显示 `--`、真实零值保留单位。冠军参考缺失按口径显示“待配置/待参考”，空图保留坐标占位，失败提供重试；训练总览、专项训练、体能训练的人员区保留每页 5 人翻页与运动员选择，不提供搜索；档案页保留按姓名或队伍搜索，档案页保留基本资料、身体成分、恢复趋势、训练对比与两个雷达分组；各业务请求失败独立显示，不用失败结果推断为零。

注册与登录的密码计算已隔离到有并发上限的工作线程，减少集中登录对训练填报的阻塞；队列满或计算超时会提示服务繁忙（HTTP 503），请稍后主动重试。本次未调整按 IP 的注册/登录限流规则。

小程序运动员新增训练会持久保存提交编号：网络超时、页面重进后恢复草稿再提交，同一编号只新增一次；修改内容或成功后开始新的填报会使用新编号，允许内容相同的不同训练。服务端每次重试仍重新校验账号和权限。旧版客户端未携带编号、教练代填及修改/删除操作不在此次新增防重范围内；无法保存本地提交编号时会提示存储错误，不发送新增请求。

### 3.2 统计与图表数据来源

- 图表与统计全部读取服务端聚合接口（如 `/api/overview`、`/api/athletes/:id/overview`、`/api/analysis/summary`、`/api/coach/daily-todos`），不在前端二次拼口径。
- 缺失值与真实 0 严格区分：未采集显示缺失（“—”或留空断线），真实 0 保留 0 值行。
- 无真实数据时，部分可视化使用客户端固定示例图形并显式标记“示例数据”；示例不入库、不参与统计、排名与评价。

## 4. 功能模块

### 4.1 训练总览（已实现）

按项目、队伍和日/周/月/自定义时间范围查看团队与个人训练全貌：训练量统计（体能与专项合并柱状图，统一按分钟比较）、五项投入摘要、强度占比（U3/U2/U1/AT/TPT/AN/ATP）、训练负荷占比（SRPE 三柱结构）、RPE 均值 ± 标准差、运动损伤环形图、生理生化热力图、每日明细与训练记录。团队视图按同队同日同一课次去重，个人视图只统计本人实际参加数据；测试摘要按测试时长统计并去重重复参与记录。各训练页面统一使用日、周、月和自定义日期范围筛选，默认查看最近一月。

### 4.2 专项训练（已实现）

一级综合页面：冠军模型（赛艇世界最好成绩、陆上赛艇按体重档位连续提供，未核验字段标注“待核实”）、专项重要数据、训练量、强度占比（固定展示全部强度分区维度，0 值行保留）、训练课占比、SRPE 负荷分析与运动员概览；专项分析提供训练量分析页签（训练次数、累计距离、训练时间、按日趋势与运动员对比）。专项测试支持标准 Excel 模板下载、上传预览、逐行校验、确认入库与现场录入。页面底部运动员卡片选择后原地切换个人分析并保留团队参照。

### 4.3 体能训练（已实现）

- **体能测试**：测试录入与趋势（按指标展示团队平均变化，个人模式叠加个人值与团队平均），参考线优先取匹配项目/性别/小项/单位的冠军模型参考值（`radar_reference_values`），回退教练目标，均缺失则不画参考线；标准对比展示当前平均值、参考值、差值与达成度。
- **训练计划**：Web `/training-plans` 通过七天周视图查看与编排队伍计划，支持周次/日期切换、逐课分类编辑、同日排序与删除、个人差异调整和最终安排预览，复用草稿保存、审核发布与版本修订接口。未保存切换会提示确认，发布前展示全周期内容、个人差异与修订摘要。周概览只汇总明确填写的计划量；未填写不当作 0。小程序首页今日计划的时长与公里数按队伍主课表去重汇总，随队伍筛选切换，不累加队员人数或个人调整；个人调整仍用于本人目标及执行率。训练名称、逐课目标、桨频、组间恢复及多个体能动作沿用内容/备注文字字段，不新增数据结构；含当前接口不支持的扩展字段的计划保留只读，避免丢字段。小程序「训练总览 → 今日训练计划标题右侧 → 训练计划」供教练创建队伍草稿、逐课编辑、设置或撤销个人差异、提交审核及确认发布；已发布计划只能创建修订草稿，重新发布后保留原版本。运动员只查看本人可见的发布版本，按具体课进入既有训练填报，填写实际时长、公里数与 RPE。旧个人及项目级专项计划保留在历史区，不自动推断队伍归属；旧个人创建、修改、删除及 AI 计划入口停用（返回 410），历史读取与导出保留。AI 生成已接入队伍计划：每日定时（默认 18:00，`AI_PLAN_GENERATE_HOUR` 可配）按真实训练数据为下一训练日生成单日草稿，教练可在小程序「AI 生成计划」手动触发、自然语言多轮修改、查看修改差异与撤销，AI 草稿必须经教练审核发布后才进入运动员正式任务列表。训练实施确认由教练在小程序逐项勾选（已执行/已取消/撤销），勾选仅代表队伍组织实施，个人完成情况继续以实际训练记录与执行率算法为准。执行分析继续使用 `/api/coach/plan-execution` 和 `server/core/plan-execution.ts`：新队伍计划按训练课及个人目标计算，未关联或缺失测量保持待确认；旧计划保留历史按天口径。未完成关联的合法历史训练不会被删除或强行归入计划。
- **体能训练**：四周力量处方维护（最多 8 个项目，重量按 `MAX × 百分比` 计算，实际均重与雷达图实时联动）、逐组计划/实际结果、统一计划入口与服务端执行反馈（在训练计划页面查看，无可靠关联不推算执行率）、五类训练结构占比、证件照绑定与四周 Excel 模板导出。运动员可查看本人历史计划并下载，实际体能结果继续独立保留。
- **体能冠军参考模型**：按项目（赛艇、皮艇竞速、激流）与性别提供成人开放组八维参考（相对深蹲、相对卧拉、相对高拉、纵跳、2 分钟卧拉、前支撑、Wingate 相对峰值功率、VO₂max），标注为估算参考；包含参考信息、对比摘要、雷达、差距表与周期趋势。仅同时拥有全国、全部项目和全部队伍权限的 DMD 可修改参考值（持久化并记审计）；测试须匹配协议与单位才参与对标。

### 4.5 运动员档案（已实现）

单页整合个人信息、制胜要素、身体成分、体能与专项训练、恢复趋势、个人 vs 团队比较、训练情况对比（训练时长/累计负荷/专项距离）、雷达模型对照（赛艇专项 5 维、体能 6 维，缺失断线不补零）、生理生化与恢复状态、伤病与疼痛趋势。支持按周/按日导出总结 PDF 与训练日志 PDF（带水印），以及 A4 力量档案导出（含肌肉解剖图、测量线、教练目标差值与规则化个人评价）。所有卡片服从全局项目与日期范围，缺失日期不补零。

### 4.6 数据管理（已实现）

统一导出保留原始业务归属及测试类型、指标代码、协议、时长；只有能够完整还原的测试才填入专用表，其余填入“其他测试”。“其他测试”明确填写测试类型时保留测试事实，未指定类型的身体指标按身体测量识别。原样导出再导入应识别为已有记录，不因导出重分类制造冲突。

统一提供 Excel 暂存导入（选择模板/上传并检查 → 人员确认 → 数据审查校对 → 确认导入 → 事务入库）、导入记录、统一导出、指标字典、指标别名与数据标准维护。

- **模板**：下载权限按账号行政、项目及队伍授权判断，不以项目是否已有队伍作为权限依据；有授权但尚未建队时可下载空模板，正式导入前需建立有效队伍。提供队员资料、训练记录、测试成绩三类分用途模板（按当前项目和队伍预填系统运动员编号、姓名、所属队伍），以及按业务分类的统一模板作为高级入口；另可导出当前权限范围内全部已入库数据。
- **人员确认**：上传解析后先识别运动员（系统运动员编号 > 项目+队伍+姓名 > 出生日期消歧），同名歧义必须人工选择关联，不跨项目、跨队伍仅凭姓名合并。同名不同编号的人员在解析、校对和提交中独立处理；只有姓名的跨表记录复用文件中唯一且无冲突的人员候选，避免重复建档；弹窗打开时会用当前可访问的在册运动员重新匹配已有草稿：队内唯一同名优先，其次为项目内唯一同名，关联后保留档案原队伍；编号指向不同姓名、同批同名多身份及多人同名仍需区分。在人员确认中选择队伍后，若同项目、同队伍、同姓名唯一对应在册档案，则自动关联并显示编号，无需再次手动关联；多个同名档案仍需区分。上传解析阶段即完成已有运动员的唯一匹配（仅一个可管理队伍时可用于同名消歧）；弹窗处理方式列显示“自动关联：姓名 · 队伍 · 编号”，首次创建者显示“新建”。待建档运动员集中弹窗确认，**最小建档只需姓名和所属队伍**；出生日期、性别等可稍后在运动员档案补充，不伪造身份信息、不创建登录账号、不收集身份证号。关闭弹窗不丢失已确认内容（保存为映射草稿，不提前写正式表）。
- **数据审查**：校对修改即最终入库值；已有运动员始终保留原队伍，导入不执行调队；文件队伍不同会提示保留原队伍，新建运动员才按确认队伍建档。空白表示未提供、不覆盖已有数据（含训练类型、阶段与强度），未填强度不默认归入 AN，真实 0 会保留；竞技水平评估可不填，只填技术等级或最好成绩时仅更新档案、不要求评估日期和总分；仅有预填人员信息、未填业务字段的训练/测试行自动忽略，无需删除未使用的工作表；标准模板的记录日期为空时使用“缺失日期时使用”所选日期，未选择则补北京时间当天；只补空白，非法日期保留原文并报错；数值列只填数字（单位见表头），非法数值保留原文并定位到工作表和单元格，整行阻断入库，需修正原文件后重传或明确排除整行；重复记录按“跳过（保留原值）/更新已有/按批次策略”处理，覆盖展示原值→新值；非法日期与缺姓名等错误行明确报错并可下载问题清单（含工作表、行号、原因）；超500条支持分页。
- **统一数据冲突审查**：身体测量、臂展及其他测试、每日恢复、训练课次、力量组次、伤病、竞技评估、基本资料与评分规则共用同一个字段比较和选择流程；每类数据只定义字段及业务唯一键。表内重复来源和数据库已有值在同一卡片按“记录 1、记录 2……”并排展示，点击字段值即选中，选齐自动保存，无需再次确认；支持直接改选。选择保存仅读取、校验及更新当前冲突组，并返回该组记录；其他组可继续操作，最终提交时仍统一校验整批数据。标题右侧支持按“记录 1、记录 2……”一键选择所有页面的待审查组；已处理组不改变，缺少该记录的组跳过，所选记录缺少冲突字段时仍保留待选，真实 0 保留，相同与单方有值的表内记录直接自动合并并保留原始来源，不展示审查卡片、不要求再次确认；自动合并不覆盖数据库；不同值不取平均、不按行顺序覆盖、不自动换算单位或舍入精度。确认结果、原始来源、操作者和时间保存在草稿中，未完成选择自动暂存，支持重新编辑。不同指标与左右侧保留独立事实，共用课次的协议单独选择；修改已有课次协议会影响该课次全部指标，界面明确提示并记录审计。已有数据被其他操作修改时拒绝按旧预览覆盖。不同次记录可以修改真实日期重新分组；仍受相应业务唯一键约束。卡片每页 8 组，原始记录按需展开；旧解析器草稿须重新解析原文件。
- **入库**：建档与业务数据在同一事务提交，失败整体回滚；结果区分新建/关联、新增/更新/跳过、补全/覆盖字段。重复上传同一文件时，未提交批次可继续校对或重新解析；已入库文件生成新批次，沿用同账号同文件已提交的唯一人员关联并重新校验当前权限；正常在册人员无需重复确认，停用或身份有歧义者仍需确认。按当前数据库补回缺失记录，默认跳过已有记录，保留原批次。已删除（停用）运动员由当前有权管理其地域、项目、队伍的管理者在人员确认中关联恢复原档案及历史数据，不启用其登录账号。旧版导入规则生成的未提交草稿须重新上传原文件解析并确认，不能直接提交；重新解析后需重新校对。

导入记录统一在“数据导入”页的“最近导入批次”中查看。待确认批次可“放弃提交”，永久删除该批次、暂存明细及候选运动员资料；已入库批次不支持此操作。历史文件在确认前不会写入正式业务表。TD、DMD 可在“指标与标准”的指标字典中编辑名称、单位及启停状态，其他角色只读。

### 4.7 组织管理（已实现）

运动员管理、教练管理、队伍管理：维护运动员主数据与档案、教练分类与人员关系（含展示用主管教练关系）、队伍与成员绑定。运动员列表展示系统运动员编号（与导入模板预填值一致，支持按编号搜索），便于教练对照模板准确关联人员。同一队伍可有多名教练，绑定队伍后默认可见本队运动员。

### 4.8 系统管理（已实现）

账号权限工作台（创建下级账号、设置角色/上级/多个行政区域/项目/队伍/启停状态，账号编号统一生成“行政区划代码-项目代码-角色代码-账号序号”）、注册审核开关与账户审核（通过/拒绝）、姓名统一修改入口（服务端校验上下级关系与数据范围）、用户自助修改密码、上级重置可管理下级账号密码、操作日志（DMD 可见最近 200 条）。

新增下级账号时，登录账号和初始密码为空白，由管理员明确设置并确认密码；关闭后清除凭据，行政区域不预填。账号格式和初始密码规则由前后端共享校验，浏览器字段标记为新账号/新密码。

业务负责人统一使用 `REG`，通过行政区域、项目和队伍授权表达管理范围。旧项目负责人账号在 API 重启时合并为业务负责人，保留账号标识和原有授权，不扩大数据范围。

账号创建和授权编辑中的行政区域采用省、市、区县级联下拉选择，切换省份或城市会清空下级选择；区县显示对应六位代码，历史不匹配区域保留显示且不能作为新增候选。数据版本和在线复核限制见 [行政区划字典来源](shared/region-data/README.md)。

运动员注册使用本人已有档案的行政归属，不继承审核人的范围；籍贯单独保存在资料中，不替代行政归属。没有具体区县或历史范围为全国、省、市级时，账号权限页显示“行政归属待完善”，有管理权限的上级可通过三级下拉补全，保存后同步账号范围和本人档案，并记录完善前后的审计日志。未确认省份的新账号，以及历史全国范围账号，需由具备全国范围且覆盖其项目、队伍的上级完成首次补全；不会向其他上级自动开放管理权限。运动员始终只能访问本人数据。

账号创建和授权编辑中的队伍通过下拉框选择，候选队伍按当前账号权限及所选项目筛选；切换项目需重新选择队伍。具备相应全部队伍权限的管理账号可选择“全部队伍”，无需手动输入通配符；已有但不在当前目录中的授权保留显示。

在账号权限页选中下级账号后，可通过“重置密码”输入并确认新密码。服务端要求操作人角色级别严格高于目标且完整覆盖目标的区域、项目和队伍范围；SCC 可重置其可管理运动员。重置保留账号启停状态，立即使旧登录会话失效，并原子记录 `RESET_ACCOUNT_PASSWORD` 审计事件（不记录密码）。新密码需为 8—72 位、包含字母和数字且不超过 72 字节、首尾不能有空白字符；当前不提供首次登录强制改密。

### 4.9 微信小程序（已实现，持续迭代）

小程序运动员档案页为具备人员创建权限且有可管理队伍的用户提供“添加运动员”入口，进入独立页面填写姓名、项目、队伍及可选性别、出生日期、备注。区域管理者按需选择授权行政归属。创建复用现有运动员接口，只创建业务档案，不创建登录账号；成功后返回并刷新选中新档案。教练及 REG、TD、DMD 可在档案卡片点击“编辑”，完善权限内运动员的基本信息、联系方式、运动信息、照片和身体成分；编辑页的项目/队伍选项受账号授权约束，保存复用原管理接口，保留既有账号关联并刷新档案。运动员本人仍只可编辑本人资料，不能自行调整组织归属。已有人员关联和账号绑定仍使用现有管理流程。

运动员登录后，体能训练与专项训练页面不展示“运动员”列表模块（含人数、档案入口和分页）；其他角色保留该模块。

原生微信小程序客户端，复用 Web 端 API、账号权限与数据库。训练总览的状态监测位于图表之前，合并当日训练待办与恢复日报未填名单，支持行内代填训练/日报、上报伤病及标记或撤销已跟进。共 13 个页面：登录、注册、训练总览（今日状态、每日训练待办、复查提醒）、专项训练、体能训练（概览/训练安排/训练记录）、档案（身体成分、训练对比、雷达对照、恢复状态、疼痛趋势、伤病上报）、资料编辑、训练填报、恢复日报、测试录入（体能/专项现场录入）、我的、隐私。支持教练代填、待办就地动作与“今日已跟进”标记、弱网草稿暂存（按“表单 × 身份”隔离）。登录/注册/“我的”页展示备案号“京ICP备2026065980号”并提供工信部备案查询入口复制。使用与排障见 [小程序说明](WeChat%20Mini%20Program/README.md)。

### 4.10 AI 训练建议（已实现，依赖配置）

- “个人档案 → 力量测试个人评价”可生成四周训练建议（未配置 AI 时使用内置规则并明确标注演示草案），教练可编辑并确认，运动员只能查看已确认版本；可导出含力量对比档案与训练建议的 PDF。

## 6. 数据库与数据流

### 6.1 数据库类型与位置

SQLite 单文件数据库，默认路径 `data/training-monitor.db`，由 `server/core/database-path.ts` 统一解析（可用环境变量 `DATABASE_PATH` 覆盖，连接前自动加载项目根目录 `.env`）。连接为 `node:sqlite` 的 `DatabaseSync`，配置 WAL、外键与 `busy_timeout=15000`。详细表清单与治理说明见 [数据库说明](docs/database.md) 与 [数据库视图](docs/database-view.md)。

### 6.2 初始化与迁移

- 启动入口 `server/core/db.ts`：连接数据库 → 旧库首次升级前保留 `*.before-reconstruction-v1` 原始副本 → `initializeDatabase()` 建表建索引。
- `server/core/db-initialize.ts` 通过“表存在性检查 + `app_metadata` 版本标记”保证**幂等**，新库旧库走同一流程，无需手工运行历史 SQL；`db-migrations.ts` 承载需保留旧数据的兼容迁移；`db-system-data.ts` 只补缺失的字典数据（强度分区、动作字典等）。
- 服务启动时自动执行兼容迁移与体能冠军参考补全；迁移只增不删，不删除真实数据。

### 6.3 核心数据表

| 数据域     | 主要表                                                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 训练事实   | `training_sessions`（一天多课次）、`training_session_segments`、`strength_result_sets`（力量组级结果）                       |
| 恢复       | `daily_wellness`（运动员 × 日期幂等覆盖）                                                                                    |
| 测试       | `test_sessions` → `test_measurements` → `metric_definitions`（含 `metric_aliases` 等字典）                                   |
| 导入暂存   | `data_import_batches`、`data_import_items`、`data_import_athlete_candidates`、`athlete_aliases`                              |
| 计划与健康 | `training_plans`（计划 JSON）、`injury_records`、`athlete_body_measurements`、`special_test_events` / `special_test_results` |
| 标准与审计 | `radar_reference_values`、`special_champion_models`、`audit_logs`、`coach_todo_followups`（仅工作流标记，不入统计）          |

新训练事实只写入 `training_sessions`、`daily_wellness` 和 `strength_result_sets`；旧 `training_records` 等历史表已从正式库移除，恢复只能依赖独立备份文件。

### 6.4 导入与落库流程

```text
下载模板 → 上传解析（analyze / preview）
   → 暂存区逐行校验（格式、数值范围、日期、单位）
   → 人工校对与运动员匹配（别名匹配 / 新建候选）
   → 选择冲突策略 → 事务提交（commit）
   → 写入正式表并回写批次追溯 + 审计日志
```

预览数据存于暂存表或进程内缓存，不直写正式业务表；提交失败不留半批。同一文件哈希与项目重复解析会先清理旧暂存批次。

### 6.5 备份

- 仅 `NODE_ENV=production` 启动自动备份：启动 5 分钟后首次执行，之后每 24 小时用 `sqlite3 .backup` 在线热备份，默认保留最近 7 天（按文件修改时间滚动计算，同日多份不会合并）。仅新备份成功后清理过期的 `jingji-*.db`，失败时不清理历史。开发、测试及未设置 `NODE_ENV` 的环境不启动备份调度器。
- 备份写入实际数据库同级的 `backups/`；默认目录 `data/backups/` 已由 Git 忽略（含 `.db`、`-wal` 和 `-shm` 文件）。忽略规则不删除现有备份。
- 本次将历史备份从 Git 跟踪列表移除，本机文件继续保留。其他已有检出目录更新到此变更前，应先在仓库外保全其中的备份及辅助文件；Git 更新会移除旧的跟踪路径。
- 构建和部署不得清理迁移前副本（`*.before-reconstruction-v1`）与既有备份；定时备份仅按上述保留规则清理自己生成的过期文件。生产环境另有每日 cron 备份与异机同步，见 [部署手册](docs/deployment-ubuntu-24.md)。

### 6.6 真实数据、演示数据与模拟数据

三个字段共同区分数据性质，统计口径不得混同：

| 字段      | 含义                                                                                                                                                                              |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `source`  | 数据来源：`athlete_self_report` / `coach_report`（正式填报）、导入批次、`metric_gap_seed`（雷达展示补种）、`synthetic_30d_current_v1` / `user_requested_simulation`（模拟补充）等 |
| `quality` | 质量：`valid` / `estimated`                                                                                                                                                       |
| `is_demo` | 是否演示记录（演示记录不进入正式统计与导出）                                                                                                                                      |

**注意**：当前 `data/training-monitor.db` 内含 2026-10-08 一次性写入的模拟批次（覆盖 79 名运动员 2026-09-09 至 2026-10-08 的训练、恢复、力量、测试与专项测试记录）。其中 `source=synthetic_30d_current_v1` / `user_requested_simulation` 的记录虽按正常统计参与计算，但**并非实测采集**；正式试点前应以确认过的真实数据替换。新库初始化还会为缺少数据的运动员补种带“估算/演示”标记的指标用于雷达展示，这些记录不会覆盖导入或手工填写的真实数据。临时生成与导入这批数据的服务代码已移除，不提供重跑命令。

## 8. 部署说明

生产部署以 [Ubuntu 24.04 部署手册](docs/deployment-ubuntu-24.md) 为准，本节只做摘要，不重复维护长篇教程。

### 8.1 生产架构与发布链路

- 架构：Mac 端用 Colima + `docker buildx` 构建 `linux/amd64` 镜像并推送阿里云 ACR → Ubuntu ECS 拉取镜像经 `compose.yaml` 运行 → Nginx 提供 HTTPS 反向代理到 `127.0.0.1:8787`。服务器不克隆代码、不构建镜像。
- 安全组仅放行 80/443（公网）与 22（限办公 IP），严禁公开 8787；域名需完成 ICP 备案。
- 容器：`compose.yaml` 固定端口映射 `127.0.0.1:8787:8787`、数据卷 `./data:/app/data`（数据库与上传跨更新持久化）、健康检查与日志轮转；镜像由 `Dockerfile` 多阶段构建（构建阶段原生架构跑 `tsc -b && vite build`，运行阶段产出 linux/amd64 镜像并安装完整依赖，`npm run start` 经 tsx 运行服务端）。
- Compose 显式设置容器内 `HOST=0.0.0.0`、`PORT=8787`，覆盖 `.env` 中同名值；宿主机仍只发布回环端口。容器与发布脚本均检查 `/health`，脚本对连接重置等错误有限重试。更新 `compose.yaml` 须单独同步到 ECS，发布脚本不会上传该文件。
- 更新与回滚：以 Git 提交短哈希为镜像标签，ECS 端更新 `IMAGE_TAG` 后 `docker compose pull && up -d`；回滚即换回旧标签。日常发布与回滚推荐直接用 `scripts/release.sh`：等待容器健康并检查 HTTP 后，保留当前版和上一成功版，自动清理本仓库其他未被容器引用的 SHA 镜像；失败不清理，首次无法确认上一成功版时跳过清理。详见部署手册第 6 节。

### 8.2 构建与启动

```bash
npm ci
npm run build
npm run start
```

### 8.3 Nginx 与 HTTPS

- HTTP 仅做 301 跳转 HTTPS；TLS 使用 TLSv1.2/1.3；反向代理传递 `Host`、`X-Real-IP`、`X-Forwarded-For/Proto`。
- 配置模板见 [deploy/nginx/jingji.conf.example](deploy/nginx/jingji.conf.example)（模板含占位域名与示例路径，实际以部署手册中的配置为准）。
- 当前使用阿里云个人测试证书，**无法自动续期**，到期需手动替换 `.pem`/`.key` 后 `nginx -t` 并 reload。

### 8.4 数据库备份

- 生产环境（`NODE_ENV=production`）启用内置定时备份：启动 5 分钟后首次执行，之后每 24 小时 `sqlite3 .backup` 热备份到实际数据库同级的 `backups/`（默认 `data/backups/`），默认保留最近 7 天，成功后才清理过期备份；依赖运行环境内 `sqlite3` CLI。
- 生产环境另配 cron 每日 03:15 备份，并将备份目录同步到 OSS 等异机位置；禁止用 `cp` 直接复制活动中的数据库文件。

### 8.5 生产环境变量

`NODE_ENV=production`、`HOST`、`PORT=8787`、`DATABASE_PATH`、`JWT_SECRET`（用 `openssl rand` 生成，不得依赖自动生成文件）、`ATHLETE_PHOTO_ROOT`、`AI_*`（可选）、`TZ=Asia/Shanghai`。`.env` 权限 600，不入 Git、不入镜像。正式上线前必须修改全部演示账号密码。

### 8.6 微信小程序发布要求

- 生产 API 必须是 HTTPS 域名；在微信公众平台将该域名登记为 `request` / `uploadFile` / `downloadFile` 合法域名。
- 发布前将 `WeChat Mini Program/config.js` 的 `API_ENVIRONMENT` 改为 `production`，`NETWORK_DEBUG` 保持 `false`，并核对小程序备案信息。
- 真机网络问题的 TLS 检查与验收步骤见 [小程序说明](WeChat%20Mini%20Program/README.md#资料保存与真机网络排障)。

### 8.7 持续集成与自动发布

- `main`/`dev` 的 push 与 PR 触发 [`.github/workflows/ci.yml`](.github/workflows/ci.yml)：静态检查、单元测试、接口冒烟、类型检查与构建；`main` 分支 CI 通过后自动触发 [`deploy.yml`](.github/workflows/deploy.yml)，复用 `scripts/release.sh` 走同一条发布链路。
- 手动发布仍然有效：Mac 本地 `bash scripts/release.sh`，或在 Actions 手动运行 `deploy.yml`（填 `tag` 即回滚到已推送的旧镜像）。所需密钥与变量见 [部署手册第 6.4 节](docs/deployment-ubuntu-24.md)。

#### Gitee Go 发布配置

[`deploy/gitee-go-pipeline.yml`](deploy/gitee-go-pipeline.yml) 先执行与 GitHub CI 对齐的阻断检查，再构建前端并归档本次提交源码。上传的 `dist` 仅供下载；手动确认 Docker 发布阶段后，Agent 直接读取本次构建的 `RELEASE_SOURCE`，校验摘要，在专用发布主机上构建 `linux/amd64` 完整镜像并推送 ACR，使用完整提交 SHA 作为标签，随后调用 `scripts/release.sh --tag` 发布到 ECS。只有构建时与 `origin/main` 一致的提交允许发布；无法确认分支时拒绝发布。Gitee 不再使用 PM2 或制品仓库的 `latest`。

首次使用前必须在 Gitee Go 配置发布阶段的真实 `hostGroupID`，选择**专用发布主机**，不要选择生产 ECS。该主机需要 Bash、Git、Docker Buildx、`flock`、`sha256sum`、SSH 和可访问 ACR 的网络；生产 ECS 沿用现有 Compose、数据卷和配置，不在生产主机上构建。

Agent 环境需提供 `IMAGE`（必须与 ECS 的 `compose.yaml` 镜像仓库一致）、`DEPLOY_HOST`、`DEPLOY_USER`、`REMOTE_DIR`、`DEPLOY_SSH_KEY`（主机上的私钥文件路径）。提前校验并登记 ECS 的 SSH 主机公钥到 Agent 用户的 `known_hosts`，并用该用户登录 ACR；也可通过 Gitee 的秘密变量同时提供 `ACR_USERNAME`、`ACR_PASSWORD`，脚本使用标准输入登录，不输出密码。不要把凭据写入 YAML 或提交到仓库。

发布主机使用锁避免同时构建发布；ECS 继续使用现有发布锁与成功版本保留策略。发布检查使用 `/health` 并设置超时和有限重试。失败不会自动恢复数据库；按现有 `scripts/release.sh --tag <上一成功标签>` 流程回滚应用镜像，数据库迁移仍需独立评估兼容性与备份。首次运行需核对 Gitee 当前插件支持的 Node 版本、直接制品引用与解压目录。

> 根目录 [DEPLOY_UBUNTU24.md](DEPLOY_UBUNTU24.md) 是早期“服务器克隆代码 + PM2 + Certbot”部署路线的记录，与现行 Docker/ACR 链路不同，仅作历史参考。

### 9.2 部分实现

- **设备接入**：仅有浏览器 Web Bluetooth 演示页，服务端无设备数据接入接口，蓝牙数据不进入正式统计。
- **冠军模型覆盖**：体能冠军参考为估算参考值（覆盖赛艇、皮艇竞速、激流成人开放组）；赛艇专项雷达与参考标准（版本 `GJ-ROW-2026.07-R1`）可用，皮划艇及其他项目的雷达维度与参考标准待单独审核与配置。
- **生理生化数据**：展示与统计链路完整，但当前库数据含模拟补充批次，实测数据待接入。

### 9.3 尚未支持

- Wingate、左右差、生理生化星级、Z-Score 参考人群与综合权重等待专家确认后启用。

### 9.4 已知问题与注意事项

- 当前库含模拟批次数据（见 6.6），不可将统计结果当作实测结论；演示数据不得进入生产统计与导出。

- 前端在浏览器 localStorage 保存 JWT，依赖严格 XSS 防护；运动员证件照经静态目录 `/uploads` 提供。

- 异常状态判断使用固定阈值（不调用大模型），阈值需与教练团队确认后调整。
- 仓库内部分早期文档已过期（如 `docs/specs/` 多个规格仍为占位、`docs/database.md` 关于旧表的描述滞后），以代码与本 README 为准，详见 [文档导航](#10-文档导航) 中的备注。

### 统一导入模板（新版）

运行 `npm run template:build` 可重新生成 `public/templates/竞迹统一数据导入模板.xlsx`。静态模板、分用途模板、统一导出和解析共用 `shared/data-import-template.ts` 的字段定义。

- 统一模板包括填写说明、数据字典，以及运动员基本资料、身体测量、体能测试、FMS测试、训练课次、力量训练组次、每日恢复、伤病记录、竞技评估、其他测试十张业务表。一个文件自动识别，不选择导入用途；未用工作表与仅预填身份的业务行无需删除。
